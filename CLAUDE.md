# Truestamp Proof Verifier -- Go CLI

Go CLI tool that cryptographically verifies Truestamp proof bundle JSON files. Compiles to a single static binary with zero runtime dependencies. No dependency on the Truestamp application.

## What This Is

`truestamp verify` reads a proof JSON file (generated by `Truestamp.Proof.generate/1` in the Truestamp service at [`truestamp/truestamp-v2`](https://github.com/truestamp/truestamp-v2)) and independently verifies the complete cryptographic chain from user claims through public blockchain commitment.

Beyond verification, the CLI exposes Unix-y, pipe-friendly sub-commands that replace the common external tool chain (`sha256sum`, `shasum`, `xxd`, `base64`, `jq`, `date`): `truestamp hash` (digests), `truestamp encode` / `truestamp decode` (byte encodings), `truestamp jcs` (RFC 8785 canonicalization), `truestamp convert {time, proof, id, keyid, merkle}` (domain conversions). `truestamp create` registers a new timestamped item in either of two modes: **external-hash** (the user submits a hash of a file they keep locally) or **claims-as-source-of-truth** (no external file: the claims content itself is what gets timestamped, gated by a server-side meaningful-content rule requiring ≥ 32-char description or non-empty metadata). `truestamp console` opens an interactive Bubble Tea TUI over an authenticated WebSocket.

Authentication is **OAuth-first, API-key-second**: a browser loopback Authorization Code + PKCE flow stores a short-lived access token plus a rotating refresh token in the OS keychain; a long-lived API key remains the CI/headless fallback. See [`kb/authentication.md`](kb/authentication.md).

## Hard rules

These are prohibitions. They are stated here rather than only in `kb/` because a rule that lives in a file nobody opened is not a rule. Each links to the reasoning.

- **Never consult the filename to determine a subject type.** The type is always read from the bundle's own signed `t` (whitepaper Appendix E.24). `cmd/download.go`'s id-shape smart default is a *different* mechanism — a download has no bundle to read yet. Do not conflate them. ([`kb/architecture.md`](kb/architecture.md))
- **Never add a flag or env var overriding the Horizon / Blockstream / NIST endpoints.** E.18/E.19/E.21 exist to consult a third party; a supported override would let whoever supplies a proof also supply the "independent" chain that confirms it. Extend the link-time test harness instead. ([`kb/external-apis.md`](kb/external-apis.md))
- **Never "sync" the two algorithm registries.** `internal/hashing` (14 entries, CLI-facing) and `internal/tscrypto` (12 entries, the Appendix E.11 wire registry) differ in cardinality *and* naming, deliberately. Widening `tscrypto` accepts a `hash_type` the server rejects; narrowing it fails sound bundles. ([`kb/architecture.md`](kb/architecture.md))
- **Never import `github.com/gowebpki/jcs` outside `internal/jcs`.** A grep gate enforces it: `grep -rn 'gowebpki/jcs' --include='*.go' . | grep -v internal/jcs` must return only test files. ([`kb/jcs-canonicalization.md`](kb/jcs-canonicalization.md))
- **Never close the gap between the two safe-integer thresholds.** `MaxSafeInteger` (2^53 − 1, producer-side reject) and `MaxExactInteger` (2^53, verifier-side warn) are one apart on purpose. Unifying them is a bug in whichever direction it is done. ([`kb/jcs-canonicalization.md`](kb/jcs-canonicalization.md))
- **Never renumber the proof type codes.** The registry in `internal/proof/ptype/ptype.go` is frozen. Branch on the integers, never on strings. ([`kb/proof-bundle-format.md`](kb/proof-bundle-format.md))
- **Never add a report group that can emit `pass` or `warn`.** E.25's containment is one-way: extra `skip`/`info` rows are conformant, extra `fail`/`pass`/`warn` are not. Adding a group is cheap; adding one in those statuses breaks conformance. ([`kb/verification-steps.md`](kb/verification-steps.md))
- **Never weaken either layer of the pre-release upgrade defense** without adding the opt-in `--pre` flag that is listed as future work. ([`kb/upgrade-and-install.md`](kb/upgrade-and-install.md))
- **Never add `Co-Authored-By` or other attribution lines to commits in this repo.**

## Version control workflow

This repo is managed with **[Jujutsu (jj)](https://jj-vcs.github.io/)**, colocated on top of the git repo. The working copy is always a jj change, so `git status` reports `Not currently on any branch` (detached HEAD) as the normal steady state: **do not warn about it and do not try to "fix" it by creating a git branch**. Prefer jj commands for everything Claude does in this repo:

| Need | Use | Avoid |
| ---- | --- | ----- |
| See working-copy state | `jj st` / `jj log` | `git status` |
| See the diff | `jj diff [-r @]` | `git diff` (works but jj is canonical) |
| Set / amend the commit message | `jj desc -r @ -m '...'` (via the `/jj-desc` skill) | `git commit -m`, `git commit --amend` |
| Start a new logical change | `jj new` | `git checkout -b` |
| Move work between changes | `jj squash` / `jj split` / `jj move` | `git rebase -i`, `git reset` |
| Push a branch / bookmark | `jj git push` | `git push` |
| Inspect history | `jj log` | `git log` (also fine; both views agree) |

Read-only `git log`, `git show`, `git diff`, `git blame`, and `gh ...` commands are fine: jj and git share the same object store. **Mutating git commands** (`git commit`, `git checkout -b`, `git reset`, `git rebase`, `git push`) should be avoided in favour of their jj equivalents so the jj operation log and bookmarks stay coherent.

**Writing commit descriptions:** use the `/jj-desc` skill (installed at the user level, in `~/.claude/skills/jj-desc/`): it analyses the diff, drafts a 50/72 message in imperative mood, and runs `jj desc -r <ID> -m '...'` after a single confirmation.

## How to Build and Run

`task build` produces `build/truestamp`. For the subcommand and flag inventory, run `./build/truestamp --help` (and `<subcommand> --help`), or read `README.md` §Commands / §Configuration. The flag semantics `--help` cannot convey are in [`kb/configuration.md`](kb/configuration.md).

Server-side cap worth knowing: `beacon list --limit N` accepts 1..100 (default 25) and the server caps it at 100.

### Pipeline recipes

```bash
# Recompute a Truestamp claims_hash locally (equivalent one-liner)
truestamp jcs < claims.json | truestamp hash --prefix 0x11 -a sha256 --style bare --no-filename
truestamp hash --prefix 0x11 --jcs -a sha256 --style bare --no-filename < claims.json

# Convert a JSON proof to deterministic CBOR and verify
truestamp convert proof --to cbor proof.json | truestamp verify --skip-external

# Derive the 4-byte kid fingerprint from an Ed25519 pubkey
truestamp convert keyid CTwMqDZnPd/QTLSq8aTeSD3a+j2DQxKcGfhhIYJQ65Y=

# sha256sum-compatible drop-in
truestamp hash doc.pdf                                # "<hex>  doc.pdf"
truestamp hash --style bsd -a sha512 doc.pdf          # "SHA512 (doc.pdf) = <hex>"
```

Exit code 0 = all checks passed, 1 = failure.

## Signature Payload Format

The signed payload is fixed-width, big-endian:

```
v(1) || t(2) || kid(4) || ts_ms(8) || subject_hash(32) || block_hash(32) || N(2) || epoch_roots(32*N)
```

- `t` = subject type code (uint16 BE); cryptographic domain separation across subject types.
- `kid` = the 4-byte key id **derived from `pk`** (`tscrypto.ComputeKeyID(pk)` = `truncate4(SHA256(0x51 || pk))`), **not** `b.kid` and **not** `s.kid`. Appendix E.9 is explicit: for this slot it MUST be the derived value and MUST NOT be read from the bundle's stored kids. Under legitimate key rotation the stored `b.kid` / `s.kid` differ from the derived one, and a verifier that fills this slot from `b.kid` rejects every rotated-key proof. The stored kids are used verbatim in the 0x13 / 0x23 subject composite and the 0x32 block hash: different preimages, different rule.
- `ts_ms` = milliseconds since Unix epoch (uint64 BE) from `ts` ISO 8601.
- For `t ∈ {10, 11}` (block-like), `subject_hash == block_hash`.
- Signed as: `Ed25519.verify(SHA256(0x61 || payload), pk)`.

## Modifying This Code

When changing verification logic, ensure it stays consistent with:

- `truestamp-v2/whitepaper/whitepaper.typ` Appendix E: the normative conformance spec, and the tiebreaker when the sources below disagree
- `truestamp-v2/whitepaper/verify_proof.exs`: the reference Elixir verifier; disagreement with it on a bundle is a defect in one of the two, so investigate rather than paper over
- `truestamp-v2/kb/cryptography/byte-prefix-registry.md` for hash domain prefixes and wire formats
- `truestamp-v2/lib/truestamp/proof.ex` for the proof bundle structure as actually produced

Read [`kb/verification-steps.md`](kb/verification-steps.md) and [`kb/proof-bundle-format.md`](kb/proof-bundle-format.md) before changing anything in `internal/verify` or `internal/proof`.

This CLI is standalone. All crypto uses Go stdlib (`crypto/sha256`, `crypto/ed25519`) plus `gowebpki/jcs` for RFC 8785 canonicalization, reached only through `internal/jcs`. External deps: `cobra` (CLI), `koanf` (config), `gofrs/uuid` (UUIDv7), `oklog/ulid` (ULID), `fxamacker/cbor/v2` (CBOR), `lipgloss` v2 (terminal styling). The `truestamp upgrade` subcommand is implemented in-house (`internal/selfupgrade`, `internal/upgradecheck`, `internal/install`) with stdlib-only crypto and an optional shell-out to the system `cosign` binary: no third-party upgrade library pulled in.
