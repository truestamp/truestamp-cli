# Truestamp Proof Verifier -- Go CLI

Go CLI tool that cryptographically verifies Truestamp proofs, one JSON document each. Compiles to a single static binary with zero runtime dependencies. No code dependency on the Truestamp application; an online run reads Truestamp's keyring.

## What This Is

`truestamp verify` reads a Truestamp proof, one JSON document generated by the Truestamp service at [`truestamp/truestamp-v2`](https://github.com/truestamp/truestamp-v2), and verifies it as an external verifier of `SPEC.md` in [`truestamp/truestamp-verification`](https://github.com/truestamp/truestamp-verification) does, through the steps of SPEC.md section 10.2 (the verification steps): the envelope and its environment marker; key binding of the signer's key against the keyring that governs the run, by default the keyring read from www.truestamp.com online and the compiled pin offline; the strict Ed25519 signature over `proof_hash`; the schema and the network pins; every hash, Merkle inclusion proof and link, recomputed from the values the proof carries; and, online, the Stellar and Bitcoin commitments and each entropy source, from which it draws the submitted-after and submitted-before edges of the submission window. A run ends in a bare rejection or in a report with one label, `verified`, `internally-consistent`, `supplied-keyring`, `unattributed` or `failed` (SPEC.md section 10.5 (Verdict and report)), and exits with the code SPEC.md section 12.2 (Exit codes) gives. `truestamp verify --remote` also asks the Truestamp service to verify the proof and prints that verdict beside the report, never as a row of it and never as a reason code. A proof has one format, SPEC.md's `version` 1, and nothing older is recognized. `truestamp inspect` reads a proof through the verifier's strict reader and SHAPE checks and prints what it carries and the values it recomputes, without verifying it; a time the proof carries is printed only as declared.

Beyond verification, the CLI exposes Unix-y, pipe-friendly sub-commands that replace the common external tool chain (`sha256sum`, `shasum`, `xxd`, `base64`, `jq`, `date`): `truestamp hash` (digests), `truestamp encode` / `truestamp decode` (byte encodings), `truestamp jcs` (RFC 8785 canonicalization), `truestamp convert {time, id, keyid}` (domain conversions). The resource groups `items`, `proofs`, `blocks`, `beacons`, `entropy`, `keys` and `teams` are the API surface; `README.md` §Commands is the inventory. `truestamp items create` registers a new timestamped item in either of two modes: **external-hash** (the user submits a hash of a file they keep locally) or **claims-as-source-of-truth** (no external file: the claims content itself is what gets timestamped, gated by a server-side meaningful-content rule requiring ≥ 32-char description or non-empty metadata). `truestamp console` opens an interactive Bubble Tea TUI over an authenticated WebSocket.

Authentication is **OAuth-first, API-key-second**: a browser loopback Authorization Code + PKCE flow stores a short-lived access token plus a rotating refresh token in the OS keychain; a long-lived API key remains the CI/headless fallback. See [`kb/authentication.md`](kb/authentication.md).

## Hard rules

These are prohibitions. They are stated here rather than only in `kb/` because a rule that lives in a file nobody opened is not a rule. Each links to the reasoning.

- **Never consult the filename to determine a subject type.** The type is always read from the proof's own signed `type`, which SHAPE checks against the schema's closed registry (SPEC.md section 10.6 (Declare and verify), rule 3), and a proof is identified by its `proof_hash`, never by its file (SPEC.md section 3.1 (The envelope)). `cmd/proofs_get.go`'s id-shape default and server-side type resolution are a *different* mechanism: a fetch has no proof to read yet, and what it resolves is which proof to request, not how one is graded. For an item asked for by its UUIDv7, its item code or its item_hash, it reads one thing of the served proof, the record's id or the item_hash recomputed from its record, to refuse a proof of a different item before anything is written; that check is never a verdict. An id argument is never trimmed, and a UUID is only its 36-character UUIDv7 text, in either case (`internal/ids.IsUUIDv7Text`, which `internal/proof.DetectIDType` and every id-taking command use). Do not conflate them. ([`kb/architecture.md`](kb/architecture.md))
- **Never let a proof choose where its evidence is read, and never add a kind of source SPEC.md does not name.** A Stellar, Bitcoin or NIST read goes to a compiled-in default or, for Stellar and Bitcoin only, to a Horizon, Esplora or Bitcoin Core server the operator pins (SPEC.md section 9 (What a verifier pins)). Nothing in the document selects a source, a network, a keyring or the environment (SPEC.md section 10.6 (Declare and verify)), so whoever supplies a proof cannot also supply the "independent" chain that confirms it. In an online run, every Stellar and Bitcoin source, compiled-in default or operator-pinned, passes its chain's production identity check both ways at CONFIGURATION, before the file is read: a source pinned to its chain's production network gives that network's value, and a source pinned to any other network does not. A mismatch is `configuration_error`; an identity read with no usable answer makes that source unreachable, so the rows it serves are `skip source_unreachable`, never a failure (SPEC.md section 10.2, step 0 (CONFIGURATION)). That check keeps a production pin from reading a test network, where blocks and ledgers are cheap to make. Source and network pins are operator configuration, and may come from the configuration file, an environment variable or a flag (SPEC.md section 9 (What a verifier pins)). The verifier's environment and keyless mode are set only by options given for the run, never by the configuration file, an environment variable, `--base-url` or the document (SPEC.md sections 6.4 (The environment marker) and 8.3 (External verifiers)), and a failed online keyring read binds no key and never falls back to the compiled pin. Tests fake the network through the test harness, never through a new option. ([`kb/external-apis.md`](kb/external-apis.md))
- **Never let a test reach the network or a stored credential.** A test talks only to an `httptest` server on loopback or to a binary whose endpoints are redirected at link time (`-ldflags -X`, as `cmd/verify_online_test.go`'s `verifierEndpointFlags` and `buildVerifyBinary` do). The cmd package's `TestMain` (`runTests` in `cmd/verify_test.go`) isolates the environment every subprocess the suite starts inherits: a HOME and XDG directories made for the run, no `TRUESTAMP_*` variable but `TRUESTAMP_NO_UPGRADE_CHECK=1`, and a dead loopback `TRUESTAMP_BASE_URL`. A test may narrow that further (the golden `--help` tests set fixed HOME paths that hold nothing) but never widen it, so no test reads the developer's configuration or an OAuth session stored for a real origin. A test whose command reads a credential or calls the API sends it to that dead base URL or to a loopback `--base-url` it passes, with a fake key where it needs one; a test written to prove that no request is sent counts the requests. The one live test, the console WebSocket check in `internal/wschannel/smoke_test.go`, stays behind its opt-in, the `smoke` build tag, and skips without `WSURL` and `APIKEY`; no agent runs it unless the user asks for that run, and then only against the server the user names. An agent runs every test, its own and a reviewer's, under the no-network guard: `task test-nonet` (`task test-nonet -- <command>` for vet, lint or one package), or, where a sandbox would nest, the lane's copy of the same guard. The guard refuses exactly every connection off loopback, loopback ports 4000 to 4003, 5432 and 4369, DNS, the Docker and Postgres Unix sockets and the keychain tool; it first runs a control that must see a refusal of each kind (off loopback, loopback ports 4000 and 5432, DNS, both sockets and the keychain tool) and the recorder log a connection, and it fails a run that passes with a recorded attempt. A child started through a SIP-protected binary such as `/bin/sh` is refused but not recorded. nonet exits 2 on a bad setup, 3 if the control fails, 4 if the command passes with a recorded attempt, and otherwise with the command's status; Task reports any failure as 201, so read nonet's code from Task's `exit status N` line or with `task -x test-nonet`. A test that needs the network is a defect to fix, never a refusal to allow. ([`tools/nonet/nonet.sh`](tools/nonet/nonet.sh))
- **Never "sync" the two algorithm registries.** `internal/hashing` (14 entries, what `truestamp hash` accepts) and `internal/verifier`'s `hashHexCharacters` (12 entries, the `hash_type` table of SPEC.md section 10.2, step 13 (EXPECTED_HASH)) differ in cardinality *and* naming, deliberately: the second is SPEC.md's, so widening or narrowing it changes EXPECTED_HASH's row on a proof every other verifier grades alike. Neither is the claims `hash_type` registry: the server decides what `items create` may send, and the CLI makes no local check of it. ([`kb/architecture.md`](kb/architecture.md))
- **Never import `github.com/gowebpki/jcs` outside `internal/jcs`.** A grep gate enforces it: `grep -rn 'gowebpki/jcs' --include='*.go' . | grep -v internal/jcs` must return only test files. ([`kb/jcs-canonicalization.md`](kb/jcs-canonicalization.md))
- **Never import `encoding/json` (v1).** JSON is read and written through `encoding/json/v2` and `encoding/json/jsontext`, with proofs, keyrings and source answers through `internal/strictjson` and `internal/jcs`, which use neither. v1 keeps the last of two repeated member names, replaces invalid UTF-8 with U+FFFD and matches field names regardless of case, so a struct a response is decoded into is tagged. `cmd/json_imports_test.go` is the gate. Every `--json` rendering goes through `emitJSON`, whose `json.Deterministic` and `jsontext.PreserveRawStrings` options keep map order stable and `inspect`'s escapes in place. A number that must stay as written in an `any` is read with `internal/jsonnumber.AsWritten`, and a field left out only at its zero value is tagged `omitzero`, never `omitempty`, which v2 no longer applies to `false` or `0`. ([`kb/architecture.md`](kb/architecture.md))
- **Never add a second safe-integer bound.** SPEC.md's MAX_INTEGER, 2^53 - 1 (section 9, What a verifier pins), is the one bound, in every path: a number is read as its nearest binary64 value, and one whose value is an integer of magnitude above MAX_INTEGER and below 10^21 is refused however it is written (`9007199254740992`, `9007199254740992.0`, `1e16`). The strict reader refuses it by rule J5 of SPEC.md section 10.1 (Parsing), `truestamp jcs` and `truestamp hash --jcs` refuse it as J5 does, and `truestamp items create` reads every claims text it sends (a claims file, claims on stdin, `--metadata` and each `--location` number) with the strict reader, so J5 refuses such a value there before anything is sent. So this CLI never accepts a file, or computes a `proof_hash` or a claims hash, over a value that every other verifier and the Truestamp service refuse. ([`kb/jcs-canonicalization.md`](kb/jcs-canonicalization.md))
- **Never give a proof type a number.** A type is its name, one of the six of the schema's closed registry (`item`, `entropy_nist`, `entropy_stellar`, `entropy_bitcoin`, `block`, `beacon`; SPEC.md section 3.2 (Members of `proof`)), compared exactly. In verification it is the only member that selects what runs, and only once SHAPE has checked it (SPEC.md section 10.2, step 7 (SHAPE), and section 10.6 (Declare and verify), rule 3). ([`kb/proof-bundle-format.md`](kb/proof-bundle-format.md))
- **Never add a report row SPEC.md does not define.** SPEC.md section 10.2 (the verification steps) fixes which rows a run reports, their parts and their order, and conformance compares every row in order, passes and skips included (SPEC.md section 13.1 (What a verifier passes)), so an extra row in any status breaks conformance, and so does a missing one. Rows and bare rejections carry only the reason codes of SPEC.md section 12.1 (Reason codes). A check the CLI needs that SPEC.md lacks is raised against SPEC.md first. What the CLI prints beside the report, such as the item code (SPEC.md section 11.5 (Display)) or the verdict `truestamp verify --remote` asks the Truestamp service for, is never a row and carries no reason code. ([`kb/verification-steps.md`](kb/verification-steps.md))
- **Never weaken either layer of the pre-release upgrade defense** without adding the opt-in `--pre` flag that is listed as future work. ([`kb/upgrade-and-install.md`](kb/upgrade-and-install.md))
- **Never classify a document by its layout.** SPEC.md's `version` 1 is the only format, and nothing recognizes an older shape: a document that is not exactly the envelope of SPEC.md section 3.1 (The envelope) is the bare rejection `invalid_envelope`, whose `sub_reason` names the first check of SPEC.md section 10.2, step 3 (ENVELOPE), that fails, and no reason code, code path or branch exists for an earlier layout. Its message is the one that step fixes, "This file is not a Truestamp proof.", and no other. ([`kb/proof-bundle-format.md`](kb/proof-bundle-format.md))
- **Never let any member but the proof's `type` select what runs.** `type`, compared with the schema's closed registry, is the only member that selects what runs (SPEC.md section 10.6 (Declare and verify), rule 3). Every other member that varies, an entropy object's `source`, a key event's `type` or the chain a commitment entry is keyed by (SPEC.md section 3.4 (Commitments)), chooses only among the alternatives the schema lists for its position, and the alternative chosen is checked in full. ([`kb/proof-bundle-format.md`](kb/proof-bundle-format.md))
- **Never invent a command verb.** Read verbs are the closed set `list` / `get` / `latest` / `current` / `genesis`; write verbs are the closed set `create` / `update` / `edit`. `show`, `view`, `describe`, `info`, `fetch`, `download`, `new`, `add`, `set` are banned as synonyms (`config show` is the one recorded exception, kb/command-tree.md R9), and `status` means credential liveness only. `edit` is not a synonym of `update`: it hands a whole document to `$EDITOR` where `update` sets named fields from flags, and it is confined to files this CLI owns (`config edit`); there is no `items edit`. A new capability is a flag (R8) unless it passes all four domain-verb tests (R5). ([`kb/command-tree.md`](kb/command-tree.md))
- **Never add a cobra help topic, or any reference documentation inside the binary.** Three existed briefly (`glossary`, `formatting`, `exit-codes`) and each was a third copy of something owned elsewhere: the vocabulary by the whitepaper in `truestamp-v2`, the output contract by `README.md`, `verify`'s exit codes by SPEC.md section 12.2 (Exit codes), which `README.md` §Exit codes lists beside the other commands' own and `truestamp schema get exit-codes` publishes, with the reason codes of SPEC.md section 12.1 in `truestamp schema get reason-codes`, and the registries by `truestamp schema` (which is generated). Prose in a Go string cannot be kept in sync with a document in another repo and no test can check it. Per-command `--help` carries the constraints that apply to *that command*. ([`kb/command-tree.md`](kb/command-tree.md))
- **Never truncate a hash, id, key, signature or any other cryptographic value in output.** Not with `…`, not with `...`, not by slicing, not by a column width, not in a table, a card, a list, a log line or an error. Render it whole in every output mode. The reasoning others have found tempting, that "the full value is on the card / in `--json` / from `get`", is rejected: a listing exists to be copied, pasted, grepped and piped, an abbreviated value serves none of those, and the abbreviation is *silent*, so a reader cannot tell a shortened value from a genuinely short one. Terminal width is the user's problem to solve, with their own pager or `--json`, and never a reason to destroy data. The item code (SPEC.md section 3.9 (The item code)) is a value of its own, not an abbreviation of `item_hash` for display: it is written from `item_hash`'s leftmost 75 bits and a check symbol, so a match shows only that those 75 bits agree. In `verify` and `inspect` output it is computed from the recomputed `item_hash`, captioned as the item code and printed beside the whole `item_hash`, never in its place and never with a pass status, and it is never a member or row of the report (SPEC.md section 11.5 (Display)); `inspect --json` carries it as the labelled member `item_code`, which `truestamp schema get item-code` documents. Everywhere else the CLI prints a code, such as the `items list` column, `items create`, URLs and file names, it is printed whole, labelled, in the one spelling of SPEC.md section 3.9 (The item code), 16 characters of the uppercase Crockford base32 alphabet with no separator, and it never stands in for `item_hash` where identity is compared; where a person names an item by its code (`proofs get`, `items get`, `items update`), the CLI checks that the served item's code (for a proof, the code of its recomputed item_hash) equals the one given, which shows only that 75 bits agree, while an item_hash given is checked whole. `cmd/list_full_values_test.go` is the regression gate; `beacons list` is the reference implementation. Two narrow exceptions, neither of them display: secret masking (`maskAPIKey`, which protects a credential), and bounding a hostile or broken server's echoed string (`internal/verify.truncateToken`, `internal/httpclient.Truncate`). ([`kb/architecture.md`](kb/architecture.md))

- **Never add an alias.** No cobra `Aliases`, no hidden shims, no `Deprecated` warnings, no flag aliases, no "was: X" pointers in help. The reorganization is a clean break; a compatibility affordance re-opens it. ([`kb/command-tree.md`](kb/command-tree.md))
- **Never register a command whose server route does not exist.** It is absent from the binary, not present-and-erroring: predicting a command correctly and then hitting "not available" is worse than the command not existing. ([`kb/command-tree.md`](kb/command-tree.md))
- **Never add `Co-Authored-By` or other attribution lines to commits in this repo.**

## Version control workflow

This repo is managed with **[Jujutsu (jj)](https://jj-vcs.github.io/)**, colocated on top of the git repo. The working copy is always a jj change, so `git status` reports `Not currently on any branch` (detached HEAD) as the normal steady state: **do not warn about it and do not try to "fix" it by creating a git branch**. Prefer jj commands for everything Claude does in this repo:

| Need | Use | Avoid |
| ---- | --- | ----- |
| See working-copy state | `jj st` / `jj log` | `git status` |
| See the diff | `jj diff [-r @]` | `git diff` (works but jj is canonical) |
| Set / amend the commit message | `jj desc -r @ -m '...'` (via the `/jj-desc` skill) | `git commit -m`, `git commit --amend` |
| Start a new logical change | `jj new` | `git checkout -b` |
| Move work between changes | `jj squash` / `jj split` / `jj squash --from X --to Y` | `git rebase -i`, `git reset` |
| Push a branch / bookmark | `jj git push` | `git push` |
| Inspect history | `jj log` | `git log` (also fine; both views agree) |

Read-only `git log`, `git show`, `git diff`, `git blame`, and `gh ...` commands are fine: jj and git share the same object store. **Mutating git commands** (`git commit`, `git checkout -b`, `git reset`, `git rebase`, `git push`) should be avoided in favour of their jj equivalents so the jj operation log and bookmarks stay coherent.

**Writing commit descriptions:** use the `/jj-desc` skill (installed at the user level, in `~/.claude/skills/jj-desc/`): it analyses the diff, drafts a 50/72 message in imperative mood, and runs `jj desc -r <ID> -m '...'` after a single confirmation.

## Signature Format

The proof is signed over the digest of its canonical form (SPEC.md section 6.1 (the signing rule)):

```
M          = JCS(proof)                    proof is the envelope's proof member
proof_hash = SHA-256(0x50 || M)            32 octets, computed and never carried
S          = Ed25519-Sign(sk, proof_hash)  pure Ed25519, RFC 8032 section 5.1.6
K, V       = the public key (32 octets) and S (64 octets), as B64U32 and B64U64
```

- The document is the envelope `{"proof": {...}, "signature": {"alg", "public_key", "value"}}` and nothing else (SPEC.md section 3.1 (The envelope)). `alg` is the literal `truestamp-ed25519-sha256-jcs`, compared with that literal and never used to select behavior. `public_key` holds K and `value` holds V, each matched against its pattern class, B64U32 or B64U64, before it is decoded, because Go's `RawURLEncoding.Strict()` skips CR and LF (SPEC.md section 2.4 (Pattern classes)).
- `proof_hash` is computed from the `proof` value as parsed under SPEC.md section 10.1 (Parsing), never taken from the received bytes or from anything the document carries, so every formatting of one value verifies alike. The message Ed25519 signs is its 32 octets: never M, and never its hex.
- Key binding (SPEC.md section 10.2, step 5 (KEY_BINDING)) comes before the signature (step 6, SIGNATURE). Outside keyless mode, the 32 bytes K decodes to must equal the 32 bytes of a key in the keyring that governs the run (SPEC.md section 8.3 (External verifiers)): online by default, the keyring read from www.truestamp.com, and a failed read binds no key; offline, the compiled pin. Keyless mode skips key binding only when the run asks for it, and says so with every verdict. K's key id, the hex of the first 4 bytes of SHA-256(0x60 || K's 32 bytes), is only an index into the keyring.
- A `key_id` or `signing_key_id` the document carries never chooses or checks the signer. DERIVE checks each one where the key-event table of SPEC.md section 3.3 (Block node, key events and genesis) names it, against its event's key (a key event's `key_id` against its `public_key`, a block record's `signing_key_id` against its event's `key_id` or `active_key_id`), and a mismatch is `key_event_mismatch`; neither ever binds the signer.
- The check is SPEC.md section 6.2 (Strict verification). Go's `crypto/ed25519` makes its steps 4 to 7 but not steps 2 and 3 (y below p, and none of SMALL_ORDER_KEYS), so the CLI makes those itself before it calls the library: on K at ENVELOPE, on every key of a keyring when it loads, on each key event's `public_key` at DERIVE, and on a rotation's `previous_public_key` as the key of its handover signature. No option skips the signature.
- The only other signature a proof carries is a rotation's `handover_signature`, verified by the same rule under `previous_public_key` over the 32 bytes of SHA-256(0x62 || JCS(the key event without `handover_signature`)) (SPEC.md sections 3.3 (Block node, key events and genesis) and 6.2 (Strict verification)). A proof carries no block signature.

## Relationship to the Truestamp service

This CLI verifies proofs generated by the Truestamp service, maintained at [`truestamp/truestamp-v2`](https://github.com/truestamp/truestamp-v2). What a proof is and how one is verified is defined in neither repository but in [`truestamp/truestamp-verification`](https://github.com/truestamp/truestamp-verification), which every verifier follows, Truestamp's own included. Each path below is relative to the repository its bullet names.

- **NORMATIVE SPEC** (truestamp-verification): `SPEC.md`, the only normative document. Section 3 is the proof document (3.9 the item code), 4 the byte-prefix registry, 5 Merkle trees and inclusion proofs, 6 signing and strict Ed25519, 7 the constructions text, 8 the verifier roles, 9 what a verifier pins, 10 the verification algorithm (10.1 parsing, 10.2 the steps, 10.5 the verdict and report, 10.6 declare and verify), 11 the submission window, 12 the reason and exit codes, and 13 conformance. Where the constructions text, the whitepaper, a knowledge base or any implementation differs from it, SPEC.md governs. **Cite a section by its number and a few words naming it, such as "SPEC.md section 10.2, step 0 (CONFIGURATION)", never by line number**: line numbers move.
- **Spec data** (truestamp-verification): `spec/`, the files SPEC.md section 9 (What a verifier pins) lists: `prefixes.json`, `constants.json`, `small-order-keys.json`, `encodings.json`, `networks.json`, `network-pins.json`, `value-classes.json`, `schema.json`, the constructions text under `constructions/`, `keyring.production.json`, `keys.nonproduction.json`, `reason-codes.json` and `exit-codes.json`. The CLI holds what it needs as compiled constants or an embedded copy, with a test that each equals its file, and reads no other repository at run time.
- **The CLI's copy**: `spec/`, `vectors/` and `MANIFEST.sha256` live under `testdata/verification/`, with a `SOURCE` file naming the spec commit they came from, and the runtime pins are embedded from a package of their own (`internal/specdata/verification/`); both change only by syncing from the spec repository with `task verification-sync`, never by hand, and `task verification-check` compares both with the commit `SOURCE` names, by hand before a sync lands. `testdata/idshape/id_shapes.json` is a copy of truestamp-v2's `test/fixtures/id_shapes.json`, the known answers of `Truestamp.IdShape`, with a `SOURCE` naming the app commit it came from; `internal/proof.DetectIDType` is tested against every row, and it changes only by copying the app's file, never by hand.
- **Conformance vectors** (truestamp-verification): `vectors/cases.json`, the offline and online cases, with the replay files of the online cases under `vectors/corpus/replay/`; `vectors/item-codes.json`, known answers for the item code, which are not conformance cases; and `MANIFEST.sha256`. A claim of conformance names the commit of that repository and the digest of `MANIFEST.sha256` (SPEC.md section 13.1 (What a verifier passes)).
- **Reference verifier (the oracle)** ([`truestamp/truestamp-verify-ex`](https://github.com/truestamp/truestamp-verify-ex)): the Elixir library `Truestamp.Verify`, offline and online (truestamp-verification itself holds no verifier). Run one proof in its checkout with `mix truestamp.verify FILE [--environment NAME] [--keyring FILE]`. That reproduces a conformance case only when the case is offline and its configuration is an environment and a keyring with that environment's default network pins, as in `mix truestamp.verify FILE --environment test --keyring PATH/TO/vectors/keyring.test.json`. Reproduce any other case with `mix truestamp.conformance CASES_JSON` (`--offline-only` leaves the online cases out), which gives each case its full configuration, network pins included, and answers each online case from its replay file. `mix truestamp.verify --online` reads the live chains, entropy sources and keyring instead, so it never matches an online case and, like any network read, is not for an agent to run. It pins its own commit of truestamp-verification (`@verification_ref` in its `mix.exs`), which can differ from this CLI's `testdata/verification/SOURCE`: compare the two before reading a disagreement as a defect.
- **Written for agents** (truestamp-verification): its README sets the goal that an agent given only `SPEC.md`, `spec/` and `vectors/` can derive a working verifier or library in almost any language, and `AGENTS.md` says how to use, test and change the repository. A rule this CLI needs that SPEC.md does not state is a gap to raise there, never one to settle only in this repository.
- **Merkle trees**: [`truestamp/truestamp-merkle-ex`](https://github.com/truestamp/truestamp-merkle-ex), whose README states the tree contract and whose `vectors/merkle.json` holds the known answers (SPEC.md section 5.1 (The tree)).
- **Proof generation** (truestamp-v2): `lib/truestamp/proof.ex` and `lib/truestamp/proof/`; `lib/truestamp/proof/verifier.ex` is Truestamp's own verifier (SPEC.md section 8.2 (Truestamp's own verifier)).
- **Background** (truestamp-v2): `kb/verification/verify-a-proof.md`, `kb/verification/proof-bundle-format.md` and `kb/cryptography/byte-prefix-registry.md` explain the format and its hashes; SPEC.md governs wherever they differ.
- **Beacons API**: `truestamp-v2/kb/api/beacon-api.md`. **Console WebSocket protocol**: `truestamp-v2/kb/api/console-websocket.md`.
- **Bitcoin parsers reference**: SPEC.md section 10.2, step 9 (DERIVE); the reference verifier's `lib/truestamp/verify/bitcoin.ex` and `lib/truestamp/verify/bitcoin/` (truestamp-verify-ex); and real Bitcoin bytes under `vectors/corpus/bitcoin/` (truestamp-verification).

## Modifying This Code

When changing verification logic, ensure it stays consistent with:

- truestamp-verification `SPEC.md`: the normative definition, and the tiebreaker when the sources below disagree
- truestamp-verification `vectors/cases.json`: the conformance cases, which `internal/vectorcases/conformance_test.go` runs from the copy under `testdata/verification/`
- truestamp-verify-ex: the reference verifier; disagreement with it on a case, at the same spec commit, is a defect in one of the two, so investigate rather than paper over
- `truestamp-v2/lib/truestamp/proof.ex` for the proof as actually produced

Read [`kb/verification-steps.md`](kb/verification-steps.md) and [`kb/proof-bundle-format.md`](kb/proof-bundle-format.md) before changing anything in `internal/verifier`, `internal/strictjson`, `internal/registry` or `internal/specdata`. Golden test data lives under `testdata/`: the spec's synced copy under `testdata/verification/` (see `internal/vectorcases`), the Merkle known answers under `testdata/merkle/` and the app's id shapes under `testdata/idshape/`.

Vocabulary, in every string the CLI prints and every comment: **commit / commitment** (never anchor), **submission window** with its **submitted-after** and **submitted-before** edges, **witness**, **head block** and **containing block**, **carried / not carried**. Truestamp proves submission timing, never creation timing.

This CLI is standalone. Crypto is Go stdlib (`crypto/sha256`, `crypto/ed25519`) plus `golang.org/x/crypto/{sha3,blake2b,blake2s}` for the eight non-stdlib `truestamp hash` algorithms; Bitcoin transactions, txoutproofs and headers are parsed in-house, in `internal/verifier/bitcoin`; RFC 8785 canonicalization is `gowebpki/jcs`, reached only through `internal/jcs`; the RFC 9162 inclusion walk is `transparency-dev/merkle`, cross-checked in tests against `golang.org/x/mod/sumdb/tlog`. Notable external deps: `cobra` (CLI), `koanf` (config), `gofrs/uuid` (UUIDv7), `lipgloss` v2 (terminal styling), `golang.org/x/crypto`, `transparency-dev/merkle`. The `truestamp upgrade` subcommand is implemented in-house (`internal/selfupgrade`, `internal/upgradecheck`, `internal/install`) with stdlib-only crypto and an optional shell-out to the system `cosign` binary: no third-party upgrade library pulled in.
