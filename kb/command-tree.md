# Command tree and verb vocabulary

The rules that decide where a command goes and what it is called. Read this **before adding any
command, group, or flag**, and before renaming one.

The tree is noun-first: resource groups are plural, and everything that operates on a file, stdin,
or a literal value stays at the root. The verb vocabulary below is closed where it says it is
closed. Its test is not that today's tree looks tidy, it is that a contributor adding a seventh
noun next year picks the right verbs without asking anyone.

## Status

**Phases 0 to 4 have landed.** The tree below is what the binary does, not a plan. What remains is
in [Deferred](#deferred), and none of it is registered in the binary (R12).

Verify the tree against this document with `truestamp schema get commands`, which is generated by
walking the live cobra tree and therefore cannot drift from it. `cmd/tree_test.go` asserts the
structural rules directly, and `cmd/docs_test.go` checks every documented invocation in this repo
against the live tree.

## The rules

### R0 — Resource groups are plural, and are namespaces, never commands

`truestamp <noun>` prints help and nothing else. Every group is configured by `asGroup` (`cmd/group.go`): its
`RunE` prints help, or errors when handed an argument that names no sub-command, so a retired spelling
fails loudly instead of printing help and exiting 0. That `RunE` is the help behaviour, not a default action.

Singular names are namespaces that own no server records: `auth`, `config`, `convert`, `schema`. A
namespace may still use `list` / `get` when it owns an enumerable registry, which is what lets
`schema` have them without being a resource group.

A bare group that runs something makes the group name mean two things, hides the default verb from
the people who most need to learn it, and forces every future noun to answer "does this one have a
default?". It also fails: `items list` needs a credential and a network round trip, so a bare
`truestamp items` on an unauthenticated machine would answer "what can I do here?" with an auth
error.

### R1 — Read verbs are a closed set of five

`list`, `get <id>`, `latest`, `current`, `genesis`. There is no sixth. Anything that looks like one
is a flag under R8 or a domain verb under R5.

### R1a — `latest` vs `current` is decided mechanically

Ask why the answer changes over time:

- Something was **appended** → `latest`. (`blocks latest`, `beacons latest`.)
- A **designation moved** to a different record → `current`. (`keys current` under rotation;
  `teams current` because the user re-points the CLI.)

A noun gets at most one of them. If you cannot say why a record is distinguished beyond "it sorts
first or last", it gets neither: use `list` with a sort or limit flag.

`keys current`, not `keys latest`, is the load-bearing example. Today they coincide, but the keyring
is populated by chain replay including prerotation events, so a published-but-not-yet-active key
would make them diverge. `current` is correct now and stays correct then.

### R2 — `current` + `use` means the user points; `current` alone means the system points

`teams current` pairs with `teams use [id]`. `keys current` has no setter because Truestamp chooses
it. The presence or absence of `use` *is* the documentation.

### R3 — Write verbs are a closed set of three

`create`, `update <id>`, and `edit`. Banned as synonyms: `new`, `add`, `set`.

`edit` was originally banned as a synonym of `update`, and it is not one. The two answer
different questions and cannot be collapsed without breaking R13:

| | `update` | `edit` |
| --- | --- | --- |
| What it changes | named fields, given on the command line | a whole document, in the user's editor |
| Interactive | no, scriptable | yes, requires a terminal |
| Input | flags (`items update <id> --tags q3`) | `$VISUAL` / `$EDITOR` on a file |

Spelling the editor capability `config update` would give `update` a second, different meaning
binary-wide, which R13 forbids; spelling it as a flag (`config path --edit`) would hide a write
behind a read verb. `edit` is therefore restricted to **a file this CLI owns**: there is no
`items edit`, and there never will be, because an item's signed fields are immutable and its
mutable ones are exactly what `items update` already sets.

One creation word across the whole binary. Every surveyed CLI that creates a **remote** resource
uses `create` — gh, op, docker, flyctl, wrangler, kubectl, gcloud, az, stripe; none use `new`, and
Azure CLI bans it by name. Every attested `new` is local scaffolding (`jj new`, `cargo new`,
`rails new`), and this CLI's scaffolding verb is already `config init`.

### R4 — Append-only nouns get no destructive verb

Not now, not later. A noun is append-only when its records are cryptographically committed or are
chain history: `items`, `proofs`, `blocks`, `beacons`, `keys`.

Ordinary mutable config nouns — `teams`, and future nouns holding endpoints or secrets — **do** get
`delete <id>` when a route exists, and the word is `delete`, uniformly.

This rule is scoped, not universal. It does not bless `retire` or any other euphemism as the
sanctioned alternative for an append-only noun; see [Deferred](#deferred).

### R5 — Domain verbs are open, one per genuine capability, subject to four tests

1. Not expressible as a read verb plus a flag.
2. Names the **purpose**, not the mechanism. `keys pin`, not `keys download`: the download is not
   the point, the frozen trust decision is.
3. Uses the project's binding vocabulary and no synonym for it. In particular **never "anchor"** —
   see `CLAUDE.md`. "Trust anchor" is a legitimate PKI term of art, which is exactly the hazard:
   it is the industry word for what Truestamp calls a commitment.
4. Duplicates no capability another group owns.

### R6 — R3 beats R5

If a capability is "change a field on an existing record", it is `update` with a flag, full stop. A
domain verb is only reachable when the operation is not a field write.

This is the tiebreak that produces `webhooks update <id> --enabled=false` rather than
`webhooks disable`.

### R7 — Derived artifacts get their own group, never a verb on the source noun

A proof bundle is derived from an item, block, beacon, or entropy observation. It lives in `proofs`
with `--type` selecting the subject. There is no `items proof`, no `blocks proof`. One place, one
flag vocabulary, one filename convention.

### R8 — Flags carry variation; verbs carry kind

If two commands return the same *kind* of thing at different detail, filtering, or verbosity, that
is a flag. This kills `items status`, `items show`, and `blocks head` before they are born.

### R9 — Reserved words

| Word | Means exactly | Never means |
| ---- | ------------- | ----------- |
| `status` | credential and session liveness (`auth status`) | a record's lifecycle state |
| `verify` | check bytes against cryptography you can recompute | ask the server whether it is fine |
| `inspect` | print what a file carries **without** verifying it | anything else |
| `init` | local scaffolding | remote creation |
| `pin` | freeze a published document to disk | any other download |
| `pull` | mirror a server-side append-only sequence locally | fetch one thing |
| `use` | point the CLI at an ambient record | anything server-side |

Never used as synonyms of `get`: `show`, `view`, `describe`, `info`, `fetch`, `download`,
`retrieve`.

`config show` is the one recorded exception. It predates the reorganization, reads no server record
(it prints the resolved local configuration), and no `config get` could sit beside it without meaning
the same thing. It is kept deliberately; `TestTree_NoBannedVerbs` exempts exactly that path and points
here.

`status` is already double-booked in this binary: `auth status` is a liveness probe, and `status` is
*also* the normative Appendix E.22 per-step vocabulary (`pass|fail|skip|warn|info`) inside verify
output. A third sense would collide with a conformance term.

There is a domain reason too. A server-reported status is a **claim**; a verified proof is
**evidence**. This CLI's whole thesis is that you do not take Truestamp's word for it, so
`items status` would put the untrustworthy answer on the shortest command. Commitment state is a row
on the `items get` card and a column in `items list`; the authoritative answer stays
`truestamp proofs get <id> | truestamp verify`, which already has an exit code.

### R10 — One output contract, with its exemptions written down

- Every command rendering a **record** carries `--json` and `--silent`, mutually exclusive.
- Commands emitting a **payload**: no flag → stdout; `-o/--out <path>` → that path;
  `--to-file` → the conventional auto-name. `-o` and `--to-file` are mutually exclusive.
- The receipt card goes to **stderr** whenever a file is written, so stdout stays pipeable.
- Binary to a TTY is refused, with a message naming both flags.
- A managed local directory is always `--store <dir>`, never `-o`. Do not mix the two idioms.
- **Exempt, explicitly:** pipeline primitives that print one bare value or raw bytes —
  `convert time|id|keyid|merkle`, `encode`, `decode`, `jcs`. `hash --style gnu|bsd|bare` stays a
  byte-identical `sha256sum` drop-in. The primitives still carry the two flags, so an explicit
  `--json` or `--silent` works; what they ignore is the ambient config-file / environment setting, so a
  `silent = true` in `config.toml` cannot silence a pipe built on them.
- `config path` is **not** exempt: it renders a record and carries the pair. Its text form keeps the
  existence note on stderr so stdout stays one line, and `config path --json | jq -r .path` is the
  capture idiom.

The exemptions are recorded here and in `README.md` §Composable pipelines; `schema get commands`
shows which commands carry the pair.

`-o` with an optional value (pflag's `NoOptDefVal`) was rejected: `-o file` then parses as `-o` plus
a positional.

### R10a — `schema` renders text and JSON from one registry, never from prose

`--json` is universal: `schema get` renders a table (or the command outline) by
default and the document with `--json`, like every other command. It is not an
exception to the contract.

Both renderings read the same in-code registry, and **no value in either is
hand-written prose**. The exit-code document is the cautionary case: its
meanings were originally written out twice, once in the JSON builder and once in
the table, and had already drifted apart by a clause before anyone read them
together. It is one slice now, and the codes are the constants that actually
produce them (`panicExitCode`, `checkExit*`), so a behaviour change cannot leave
the document describing the old contract.

A document's one line of context is a `note` on the document, emitted in **both**
renderings. A footnote living only in the text is prose the JSON consumer never
sees.

**A note describes its own document and names no command.** The subject-types
note originally ended "`truestamp inspect` prints the code beside the name",
which was true when written and false one commit later, when `inspect` stopped
reporting the code. Behaviour is documented next to the behaviour, in that
command's own help, where changing one without the other is obvious. A test
enforces it.

Booleans render as their literal value, never as a marker or a blank cell: a
blank is indistinguishable from a missing one, and it makes the text quietly
carry less than the JSON.

`TestSchema_TextAndJSONCarryTheSameFacts` enforces all of it by walking the JSON
and asserting every value appears in the text. It has already caught two real
defects: a `legacy` column rendered as a marker so `false` never appeared, and a
meaningless `"legacy": false` copy-pasted onto every subject type.

### R11 — Read-only is a property, not a deficiency

If the product does not let you write a noun, do not invent `create` / `update` for it. Make it
legible: the group's `Short` begins with `Read-only:`.

### R12 — Server-blocked commands are not registered

**A bare flag name in `cliEnums` is the same hazard as a bare key in
`flagKeyMap`.** It applies the enum to every command carrying a flag by that
name, so the shell offers values the others reject. `--type`, `--format` and
`--to` each collided: `convert id --type` was offered the six proof subject
types, and `encode --to` was offered `json|cbor`. Scope by `<command path>|<flag>`
whenever more than one command carries the name;
`TestSchema_NoUnscopedEnumForACollidingFlag` fails otherwise.

**This governs help text too, not just commands.** A page describing capability
that is not reachable from this binary is the same placeholder with no command
attached. Describing a real constraint is expected — "claims are immutable", "a
proof cannot be generated until the item is committed". Promising a capability,
or documenting a pending one, is not.

A command needing a route that does not exist is absent from `--help` and absent from the binary. It
lives in this document only.

Predicting a command correctly and then hitting a runtime "not available" is the worst failure mode
available, worse than the command not existing.

### R12a — The binary does not carry reference documentation

No cobra help topics. Three briefly existed — `glossary`, `formatting`,
`exit-codes` — and each was a third copy of something already owned elsewhere:

| Was duplicating | Owned by |
| --------------- | -------- |
| the vocabulary | `whitepaper/whitepaper.typ` and `kb/glossary/` in truestamp-v2 |
| the output contract | README §Global flags and R10 above |
| the exit codes | README, and `schema get exit-codes`, which is generated |

Prose in a Go string cannot be kept in sync with a document in another
repository, and no test can check that it is. That is the same drift hazard
`CLAUDE.md` already names as a hard rule for the two algorithm registries, and a
glossary is worse than a registry because being subtly out of date reads as
authoritative.

A `destructive` topic also existed and opened with "Nothing in this CLI
currently deletes a Truestamp record" — a page about capability that is not
here, which R12 forbids.

What replaces them: each command's own `--help` carries the constraints that
apply to *that command*, because those are facts about it rather than about the
product. `truestamp schema` carries the machine-readable registries, generated
from the tree so they cannot drift.

### R12b — Text the binary prints may not name a command that does not exist

An audit of every printed string found four places telling the user to run a
retired command, and **all four were runtime hints rather than help fields** —
the place nobody thinks to check. `beacons list` and `teams list` each printed a
hint naming a retired command, `teams create`'s success card closed by telling
the user to run one, and the console's Teams pane named two at once.

`TestTree_EveryCommandNamedInHelpTextExists` walks every string literal under
`cmd/` and `internal/` via the AST and resolves each invocation against the live
tree. Three details make it work:

- **Literals, not raw text.** A comment explaining that `truestamp convert
  proof` used to exist is legitimate history; grepping would flag it.
- **Quoted or indented only.** Unindented line-initial text is wrapped prose or
  an output message — "truestamp is up to date (%s)" — and matching it produced
  four false positives.
- **Resolve, do not shrink.** Shrinking a path until something resolves accepts
  a prefix, so `truestamp teams set` passes because `teams` exists. The test
  walks the tree and reports the first word that is not a sub-command of what
  came before.

### R13 — Flags obey the same discipline: one word, one meaning, no aliases

The clean break was mandated for commands; flags do not get an exemption.

- No flag aliases. `verify --hash` (alias of `--expected-hash`) and `verify --skip-external`
  (alias of `--offline`) are removed.
- One word, one meaning, binary-wide. `--hash` meant the hash of *your* data on `create` and the
  hash you *expect* on `verify`; the former is now `--data-hash`.

## Applying the rules to a new noun

Worked cold against a hypothetical `webhooks`. No step needs a judgement call, which is the point.

| Question | Rule | Answer |
| -------- | ---- | ------ |
| Bare group? | R0 | prints help |
| Many rows, addressable by id? | R1 | `webhooks list`, `webhooks get <id>` |
| Distinguished record? | R1a | no head, no designation → no `latest`, no `current`, no `use` |
| Writable? | R3, R11 | `webhooks create`, `webhooks update <id>`; `Short` does not say `Read-only:` |
| Append-only? | R4 | no, mutable config → `webhooks delete <id>` exists |
| Disable one? | R6 | `webhooks update <id> --enabled=false`, not `webhooks disable` |
| Send a test event? | R5 | passes all four tests → `webhooks test <id>` is legitimate |
| Delivery health? | R8, R9 | not `webhooks status` — a field on `get`, a column on `list` |

The headings are the cobra `AddGroup` headings root help prints (`cmd/root.go`), not commands. Each
flag list is the command's own; the root persistent flags (`--base-url`, `--api-key`, `--team`,
`--config`, `--http-timeout`, `--log-file`, `--log-level`, `--no-color`, `--no-upgrade-check`) apply
everywhere and are not repeated. `truestamp schema get commands --json` is the generated,
authoritative form of this picture; this one is the reader's overview.

### Clean break

Old names do not survive in any form: no cobra `Aliases`, no hidden shims, no deprecation warnings,
no "was: X" pointers in help text. Gone with no replacement pointer: root `create`, root `download`,
`convert proof`, `beacon` (singular), `beacon by-hash`, `team` (singular), `team show`, `team set`,
`team unset`, and every bare-group default action.

The break extends to the configuration surface, but **not** to the `team` config key. R0's plural
rule governs command groups, not settings: `--team <id>`, `team = "..."` and `TRUESTAMP_TEAM` each
name exactly one team, and singular is correct for all three. What did move is `silent` / `json`,
from `[verify]` to the top level (they are CLI-wide, not verify's), and `verify.skip_external`,
renamed `verify.offline` to match the only flag that sets it.

`internal/config/defaults/config.toml` names commands in prose that goes stale, and `config init`
is idempotent, so an existing user's on-disk file keeps stale comments forever unless it is handled
deliberately.

## Notes that constrain implementation

### `items update` is safe, and moves teams

`PATCH /items/:id` routes to the Ash `:update` action, which is `accept [:team_id, :visibility,
:tags]` — "considered mutable and not included in the item's hash". `name` and `description` live
inside `claims` and are immutable. So `items update` cannot touch a signed field, and it gains a
third capability worth surfacing: moving an item to a different team.

### `proofs get` may resolve its own subject type

`POST /api/json/utilities/resolve-id` classifies an opaque id and returns its kind, proof type,
state, and block hash. `--type` is therefore **optional**: supplied, it is used; omitted, the CLI
resolves it in one extra round trip. This is the one place the id-shape dispatch used by
`beacons get` cannot work, because blocks, beacons, and entropy observations all share the UUIDv7
shape.

`proofs get`'s id-shape default is a *different* mechanism from reading a bundle's signed
`type`, and the two must never be conflated — see `CLAUDE.md`.

### `blocks` and `beacons` are two groups over one row

A beacon is a virtual four-field projection over the same block row; there is no beacon table. They
stay separate because:

1. The server draws this exact line and points across it: `kb/api/beacon-api.md` says block
   internals are deliberately not part of the beacon shape and a consumer who needs them fetches
   `GET /api/json/blocks/:id`.
2. They are cryptographically distinct subjects. ptype 10 and 11 sign the same block hash under
   different type codes; a beacon signature does not verify as a block signature.
3. Different populations. Only finalized or committed blocks project as beacons; `blocks` sees every
   state. So `blocks latest` (the head block, routinely not yet finalized) and `beacons latest` (the
   most recent finalized block) return **different rows** most of the time. They are two questions,
   not two spellings.

Both help texts must cross-reference the other.

### `blocks get <hash>` has no server-side guard

There is no by-hash route for blocks, so it goes through `filter[block_hash]=`. The beacons by-hash
action regex-guards `\A[0-9a-f]{64}\z` specifically because an unguarded cast raises a raw
`Ecto.Query.CastError`, a 500 that leaks SQL. This filter has no such guard: **validate the hex shape
client-side before sending**. The server does not assume block-hash uniqueness either, so more than
one row is an error the CLI reports, never a row it picks.

### No block height column, ever

`block_height` is a runtime `COUNT(*)` calculation, explicitly non-sortable and non-filterable, and
withheld from the wire. A block is addressed by UUIDv7, which is also the ordering handle.

### Two different things are called "commitments" on a block

The `commitments` relationship in the block's JSON:API includes is subject Merkle inclusion — the
items and entropy in *this* block's tree. The public-chain commitment is `external_commitments`,
which is **not** includable and costs extra round trips. Hence `--commitments` is designed as a flag
on `blocks get`, not a default. It is deferred: the flag is not registered yet.

### Entropy needs a discovery path

`proofs get --type entropy_nist|entropy_stellar|entropy_bitcoin` takes UUIDv7s that nothing else in
the tree surfaces. `entropy_observations` *is* in the block's includes list, so a deferred `blocks get
--entropy` is that path. Until it lands, three of the six frozen ptype subject types name resources
with no route into the tree.

### `keys` complements `verify --keyring`; neither subsumes the other

`--keyring` names a **file** and is a verify input. `keys` names a **resource group**. Different
things at different levels, no cobra conflict. `verify.keyring` stays in the `[verify]` config
section: it configures verify's behavior, and moving it to `keys.*` would be renaming a setting to
match a menu.

`convert keyid` keeps kid derivation. It is a pipeline primitive printing one bare line of 8 hex
characters; `keys` is a resource group rendering records. There is no `keys fingerprint`.

### The keyring has exactly four fields, and that constrains the UI

Each entry carries `key_id`, `public_key`, `sequence`, `active`. There is **no revocation flag, no
validity interval, and no timestamp anywhere**. A compromised key appears as an ordinary inactive
entry, indistinguishable from a routinely retired one.

So `keys list` must never render a "status", "valid until", "expires", or "revoked" column. The
honest columns are exactly `SEQ · KEY ID · PUBLIC KEY · ACTIVE`. (A stale server doc claims the
keyring carries `prerotation_commitment`; the controller does not emit it.)

Production sits at sequence 0 with a single key, so the multi-key path must be tested deliberately —
it will not be exercised by accident.

`GET /.well-known/keyring.json` is unauthenticated, which makes `keys` the only group that works
with no credential. Say so in its help.

Phases 0 to 4 are done. Two things from phase 4 remain open and are tracked here rather than
silently dropped:

- **Console parity.** `internal/console/newitem.go` is a second write surface for `items create`,
  with its own field labels, its own claims-only meaningful-content copy, and its own error
  vocabulary. Nothing requires the two to stay aligned.
- **`console`'s first-run team-persist side effect** writes config on behalf of a TTY user with no
  team configured. `teams use` is now the explicit way to do that, so the implicit write should
  either go or be stated.

### Phase 0, as landed

- `download`'s local `-o/--output` became `-o/--out`. Cobra resolves a local flag ahead of an
  inherited one, so any output flag added at root would have been shadowed and `--output json` would
  have written a file literally named `json`, silently, exit 0. `MarkDeprecated` does not fix this;
  it only warns while the flag keeps shadowing.
- `internal/config`'s `flagKeyMap` maps bare flag names **globally**, so `json` → `verify.json`
  applied to every command that registered a `--json`. Fixed by moving both settings to top-level
  keys rather than by adding a per-command registry: they are genuinely CLI-wide, and after the move
  no two commands share a flag name with different meanings. **That hazard returns** the first time
  two do; the registry is the fix at that point.
- `--silent` / `--json` mutual exclusion moved from verify's `RunE` into `config.Load`, so it holds
  for every command and a new one cannot forget it.
- Exit codes: `upgrade --check`'s exit-1-means-success-with-news overload now sits behind an
  explicit `--exit-code`, and the default is 0 for every outcome.
- Two hangs fixed. `inputsrc.IsStdinTerminal` was the inverse of a `ModeCharDevice` test, which
  `cmd/upgrade.go` already documented as too lax: `/dev/null` is also a character device, so
  `verify --file </dev/null` looked like a TTY and blocked forever in the picker under any pty.
  `cmd/items_create.go` called `ui.PickFile` with no terminal check at all. **`IsStdinPipe` and
  `IsStdinTerminal` are now independent and must stay that way** — they answer different questions,
  and `/dev/null` is what separates them (no data to read, and no terminal to prompt). Collapsing
  them made `truestamp hash </dev/null` hash the empty string instead of printing help.
- `--no-color` and `NO_COLOR` were honored only on `lipgloss.Println`. `Style.Render` always embeds
  escapes and a colour-profile writer strips them at write time, so `fmt.Fprintln(w,
  style.Render(...))` kept them. `internal/ui` now provides `Fprint` / `Fprintln` / `Fprintf` and
  every write to a **final output destination** goes through them. Writes into string builders
  deliberately do not: stripping there would remove colour before it ever reached a terminal.
- The `--json` payload shapes were left alone. `verify --json` keeps the server's field names,
  `hash --json` keeps its bare array, and `beacon --json` keeps the raw API response. R10 mandates
  the *presence* of `--json` on record-rendering commands, not a uniform envelope around it.

## Deferred

Designed, deliberately not built, and **not registered in the binary** (R12). Each needs its own
discussion before implementation.

| Deferred | Why it waits |
| -------- | ------------ |
| `keys pin`, `keys diff` | A keyring miss is a hard `fail` in `internal/verify/steps_signature.go`, so a keyring pinned today plus a legitimate rotation tomorrow reports FAIL on a good proof, with a message asserting the bundle was not signed by a published Truestamp key — which is false. Needs a design that survives rotation. See [Pinning](#pinning-what-it-buys-and-what-it-costs). |
| `blocks pull`, `blocks verify` | The local-store design (`--store`, resumable keyset paging, the chain walk) needs its own pass, including whether `verify` gains `--chain <store>` so a bundle's carried `block_path` can be checked against a chain you mirrored. |
| `keys events` | Key events live in the block `metadata` that `blocks pull` mirrors, so this is a **local** scan once the chain is on disk — and a local scan is the only form worth trusting, since the point is surfacing `emergency_rotation`. Follows `blocks pull`. |
| `proofs list` | There is no proof table; bundles come from `POST /proof/generate` and are never stored. It becomes honest when a local bundle store exists, at which point it is a *local* listing and its help must say so in its first line. |
| Item retirement | The server has `:redact`, `:unredact`, `:schedule_deletion`, `:cancel_deletion`, `:expedite_deletion`, `:hard_delete`, `:destroy_uncommitted` and a state machine, all reachable only from the LiveView UI. Needs server routes **and** a verb decision: R6 says that if retirement is reachable through the existing PATCH it is `items update --<field>`, not a domain verb. |
| `teams update`, `teams delete` | No `PATCH /teams/:id` and no delete route exist. |
| Block read-route optimizations | `get_current_head`, `get_genesis_block`, and `get_blocks_by_hash` all exist server-side with code interfaces, but `blockchain.ex` routes only `:read`. The payoff is a **guarded** by-hash route, not a call-count saving. Block's `:read` also declares no `default_limit` and no `max_page_size`, against a table growing ~1,440 rows/day. |

### Pinning: what it buys, and what it costs

Kept here so the research is not lost when the design is revisited.

The bundle-carried key proves nothing about identity. An attacker who fabricates a bundle signs it
with their own key and embeds their own public key; every step up to the key binding still passes,
because the bundle is self-consistent by construction. The keyring answers the one question the
bundle cannot self-answer: *is this key Truestamp's?*

Pinning defends against a different attacker than a live fetch. A live fetch trusts the TLS chain of
Truestamp's own domain **at fetch time**. Whoever can mint a certificate for that host — DNS or BGP
hijack, a rogue CA, a compromised cert — or who controls a future Truestamp, can serve a keyring
containing *their* key, and a forged bundle then verifies. Pinning freezes the answer at a moment
**you** chose, so later compromise cannot retroactively validate a forgery.

What pinning does **not** give you, stated so no help text overstates it:

- It does not establish the key was **uncompromised**. There is no revocation flag.
- It does not establish the key was **valid at signing time**. There are no timestamps.
- It does not establish the key was **authorized**. An attacker holding the current signing key who
  can write a block can perform an `emergency_rotation` to a key of their own, and that key then
  enters the keyring by legitimate chain replay. The design does not prevent this; it makes it
  visible on-chain.
- It is still a document served from **Truestamp's own domain**. Pinning shifts *when* you trusted
  that domain; it does not remove the domain from the trust path.

The strictly stronger artifact is the bundle-carried `signing_key_event`, which establishes that the
key was introduced by a block whose hash sits under a root recorded on a public blockchain, and which
stays checkable long after Truestamp is gone.

Whatever `keys diff` becomes, it must distinguish a routine append (a higher-sequence entry with the
active flag moved) from a red flag (an existing entry whose `key_id` or `public_key` *changed*, or a
lineage that no longer extends the pinned one) — while being honest that the four-field document
cannot tell you whether a new key arrived by scheduled or emergency rotation.

### `blocks verify`: the trap to write down before it is written

The block-level signature is over the **raw 32 bytes of `block_hash`** — decode the hex and verify
directly. That is **not** the proof-bundle rule, which is `Ed25519.verify(SHA256(0x61 ‖ payload))`
over the fixed-width payload. Same key, different message. A `blocks verify` that reuses
`internal/verify`'s signature path will reject every valid block.

Two primitives already do most of the work: `blockHashFromMap` in `internal/verify/steps_block.go`
recomputes the 0x32 block hash from the same five fields, and `walkBlockPath` in
`internal/verify/steps_witnesses.go` already walks a `previous_block_hash` chain oldest-first,
recomputing each hash and threading it forward. The server ships `Verification.verify_chain/1` as a
reference oracle to test against.
