# External API Calls

This file is the answer to "what does `truestamp verify` talk to?"; keep it exhaustive. An online run reads nothing outside the proof but these, and `--offline` reads none of them (SPEC.md sections 9 (What a verifier pins) and 10.4 (Chain and source reads)). The proof never chooses one: no member of the document selects a source, a network, a keyring or the environment (SPEC.md section 10.6).

| Service | When | Where |
| ------- | ---- | ----- |
| Truestamp's keyring | CONFIGURATION, an online run under E_v `prod` with no `--keyring FILE` and outside keyless mode | `https://www.truestamp.com/.well-known/keyring.json`, compiled in (`internal/verifier`'s `currentKeyringRead`); an explicit `--base-url` naming another origin reads `{origin}/.well-known/keyring.json` instead, as a supplied keyring |
| Stellar Horizon | CONFIGURATION (the identity read: the root's `network_passphrase`), then CHAIN (each Stellar commitment entry) and SOURCES (each Stellar entropy object) | `--horizon` / `TRUESTAMP_VERIFY_HORIZON` / `verify.horizon`, else the built-in `https://horizon.stellar.org` (public) or `https://horizon-testnet.stellar.org` (testnet) |
| Bitcoin Esplora | CONFIGURATION (the identity read: the block at height 0), then CHAIN (each Bitcoin commitment entry and `genesis.bitcoin`) and SOURCES (each Bitcoin entropy object) | `--esplora` / `TRUESTAMP_VERIFY_ESPLORA` / `verify.esplora`, else the built-in `https://blockstream.info/api` (mainnet) or `https://blockstream.info/testnet/api` (testnet); regtest has none |
| Bitcoin Core | as Esplora, over JSON-RPC (`getblockhash`, `getblockcount`, `getblockheader`) | `--bitcoin-core` / `TRUESTAMP_VERIFY_BITCOIN_CORE` / `verify.bitcoin_core`; no default. Its RPC credentials come from `verify.bitcoin_core_user` / `verify.bitcoin_core_password` or `TRUESTAMP_VERIFY_BITCOIN_CORE_USER` / `_PASSWORD` only, sent as Basic authentication and nowhere else |
| NIST Randomness Beacon | SOURCES (each NIST entropy object): `chain/{chainIndex}/pulse/{pulseIndex}` | `https://beacon.nist.gov/beacon/2.0`, compiled in (`internal/verifier`'s `nistBeaconBase`); it is one source, and no option names another |

Several sources for one Stellar or Bitcoin network, in an order and under a policy (`first`, `at_least N`, `all`), come from `[verify.sources.<chain>.<network>]` tables in `config.toml` alone (SPEC.md section 9, "Several sources for one network"). Each source's identity is read live before the file is read, and a source that answers for a network its pins forbid is `configuration_error`; one that gives no usable answer serves its rows as `skip source_unreachable`. Every read follows no redirect and ends within one deadline. A source URL that carries user information is refused wherever it comes from, and a report names a source as `scheme://host[:port]` only, since a hosted node's path can carry an API key.

The two compiled-in addresses, the keyring's and NIST's, are string variables only so that a linker can set them: the cmd package's test binary sets both to a loopback port (`-ldflags -X`, `cmd/verify_online_test.go`), so no test of the built command reads either, and no shipped build sets them (`TestShippedBuilds_SetNoVerifierAddress`, `internal/verifier`'s `TestEndpoints_ShippedValues`). Every online `verify` run in the cmd tests goes through `verifyCLI`, which refuses one that does not give a loopback source for every network its E_v pins (a `[verify.sources]` table for that network, or a floating source that serves it; under dev and staging both an Esplora server and a Bitcoin Core node), or that names a source or a `--base-url` off loopback, and fails a run whose report names a built-in source; `TestVerifyRuns_GoThroughVerifyCLI` scans the tests for a run of verify, or of the test binary, that does not go through it. Do not add a flag, a configuration key or an environment variable for either address, and do not let a document reach one.

`verify --remote` also posts the proof to `{base-url}/api/json/proof/verify`; its answer is printed beside the report and never changes it. `internal/verify` serves only `verify --remote` (and `inspect`, which reads no service). `truestamp keys list`, `keys get` and `keys current` read the keyring at `{base-url}/.well-known/keyring.json` through `internal/external`, which holds nothing else; the verify command does not use it.
