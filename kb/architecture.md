# Architecture Notes

Design decisions and their reasoning. Upgrade/install internals live in
[upgrade-and-install.md](upgrade-and-install.md).

## Conformance

- **Conformance is a maintained property, held by the spec's own vectors**: `truestamp verify` is an external verifier of SPEC.md in truestamp-verification, and the CLI passes every case of its conformance vectors (SPEC.md section 13). The copies it is held to change only by syncing, never by hand:
  - `testdata/verification/` holds the spec's `spec/`, `vectors/` and `MANIFEST.sha256`, and `internal/specdata/verification/` the `spec/` files the binary embeds (the runtime pins), each with a `SOURCE` naming the spec commit. `task verification-sync` copies them from one commit on the spec's main; `task verification-check` reads that commit again and compares both copies with it, by hand before landing a sync; `internal/specdata`'s tests hold both copies to the manifest and to each other.
  - `internal/vectorcases/conformance_test.go` runs every case of `vectors/cases.json` through the one runner (`internal/vectorcases/runner_test.go`), each online case answered from its replay file, and compares what SPEC.md section 13.1 compares; it also runs each case through `verifier.Verify`, the path `truestamp verify` runs, and requires the same encoded report or rejection byte for byte but for `fetched_at`. It logs the claim of conformance: the commit `SOURCE` names and the SHA-256 of `MANIFEST.sha256`. See [verification-steps.md](verification-steps.md).
  - `testdata/merkle/` holds truestamp-merkle-ex's `vectors/merkle.json` with its `SOURCE` (`task merkle-vectors-sync`, `task merkle-vectors-check`), the known answers of the RFC 9162 trees `internal/registry`'s walk is checked against.
  - `testdata/idshape/id_shapes.json` is a copy of truestamp-v2's `test/fixtures/id_shapes.json`, the known answers of the app's id classifier, with a `SOURCE` naming the app commit; `internal/proof`'s `DetectIDType` and `internal/ids` are tested against every row, and the copy changes only by copying the app's file.
  - The acceptance run must be **hermetic**. A keyring comes from the run's own `--keyring FILE`, never from the configuration file or an environment variable, but `--offline` is a config key, so an ambient `TRUESTAMP_VERIFY_OFFLINE` makes a run offline; the cmd package's `TestMain` clears every `TRUESTAMP_*` variable for that reason.
- **The rows are SPEC.md's, and only SPEC.md's**: a failure at steps 0 to 3 is a bare rejection, and everything after the gate is a row whose step, part, status and code SPEC.md section 10.2 fixes. An external source that is *unreachable* never fails a proof: its rows are `skip source_unreachable`, and only a source that answered and contradicted the proof fails one (SPEC.md section 10.4). `internal/verifier/source` reads the sources and `internal/verifier/source_outcomes.go` combines their outcomes under the network's policy; no other code makes that distinction.
- **The filename never decides a subject type**: `truestamp verify` reads the type only from the proof's own signed `type`, which SHAPE checks against the schema's closed registry (SPEC.md section 10.6, rule 3), and has no option that asserts one. `cmd/proofs_get.go`'s type resolution is a **different and legitimate** mechanism: it keys on the *id shape* (an item code means `item`, a 64-hex `item_hash` needs `--type item`) and, for a UUIDv7, asks the server what the id refers to, because a fetch has no proof to read yet. It decides which proof to *request*; the proof that comes back is still verified against its own signed type. Do not conflate them. For an item asked for by its UUIDv7, its code or its `item_hash`, `internal/proof.CheckServedItem` reads one thing of the served proof, its record's id or the `item_hash` recomputed from its record, to refuse a proof of a different item before anything is written; that check is never a verdict.
- **A bare rejection carries a reason code and nothing else**: a failure at steps 0 to 3 (SPEC.md section 10.2, the gate) gives no report, only `{code, message, sub_reason}`, with `sub_reason` for `malformed_json` and `invalid_envelope` alone; `cmd/verify.go` writes it with JCS under `--json`, and as `Rejected:` with the message otherwise. Two independent verifiers are compared on the code and sub_reason, never on prose (SPEC.md section 12.1).

## Code organization

- **Authentication is a single process-wide chokepoint**: `cmd/root.go`'s `PersistentPreRunE` resolves one `auth.Authorizer` via `auth.Resolve` (precedence: explicit `--api-key`/`TRUESTAMP_API_KEY` → stored OAuth session → config-file `api_key` → none) and installs it with `auth.SetDefault`, mirroring `httpclient`'s package-global pattern so the existing call sites authorize via `auth.AuthorizeRequest`/`auth.Default()` without threading an authorizer through every signature. OAuth and the API key are unified behind the same `Authorizer` (both presented as `Authorization: Bearer <value>` to the JSON API). A reactive **401 → ForceRefresh → retry-once** `http.RoundTripper` (`auth.NewRetryTransport`) is layered onto the shared client via `httpclient.SetTransport`, so a server-rejected OAuth access token self-heals without a spurious auth failure; only OAuth-mode requests *we* authenticated are retried, and a dead session (`invalid_grant` ⇒ `ErrSessionExpired`) is not. OAuth tokens live in the OS keychain (0600-file fallback), never config.toml; the refresh token rotates on every refresh. Full model in [authentication.md](authentication.md).
- **Rate limits are retried once, in one place per surface**: every Truestamp surface refuses an over-limit request with `429` and the error code `rate_limited`, naming the wait in a `Retry-After` header (refusals from the per-surface request-rate plug) or in `meta.retry_after_ms` (a limit raised inside an action; `null` means the request costs more than the limit allows and can never be admitted) and the applicable limit in `meta.limit`. `internal/jsonapi.Send` is the one JSON:API send path (the resource packages via `DoRaw`, the raw proof route `proofs get` reads, id resolution, `verify --remote` and `auth status`'s probes all go through it): it reads the header, else the meta, else `httpclient.DefaultRetryAfter`, repeats the request once after that wait plus `httpclient.Jitter` (a uniform draw below `httpclient.RetryJitter`, 2 s, because the server's per-address guard is a window aligned to the clock minute and every client it refuses is told the same second; the per-caller budget is a token bucket whose `Retry-After` is the caller's own short wait, where the draw is merely harmless; truestamp-v2 `kb/api/json-api.md` asks for exactly this), never on `null`, and not when the wait is over `httpclient.MaxRetryAfter` (the jitter is added after that decision, so it never turns a retry into a refusal). `ParseError` carries `RetryAfterMS`, `NeverAdmitted` and `Limit` on a `429`; `cmd.describeRateLimit` is the one rendering (`rate limited (retry after Ns, limit L): <detail>`); `cmd/root.go` installs the stderr "retrying in Ns" notice through `jsonapi.SetRateLimitNotifier` (terminal only, never under `--silent`, always a log line). The OAuth endpoints get the same policy from `httpclient.NewRetryAfterTransport`, keyed on status and header only ([authentication.md](authentication.md)). The verifier's keyring, Horizon, Esplora, Bitcoin Core and NIST reads, and the upgrade check's GitHub read, are deliberately not retried: a rate limit there leaves the keyring unread (`keyring_unavailable`), the source unreachable (`skip source_unreachable`, SPEC.md section 10.4) or the upgrade check failed, and a retry would change what the run reports. `meta.limit` is shown as the server sent it, never with an assumed window: the limits are server configuration and this CLI states none as a guarantee.
- **Logic/presentation separation**: `internal/verifier` makes every step and every row (each step in its own file, `outcome.go`'s `Verify` running them in order) and builds the report of SPEC.md section 10.5 (`report.go`); it reads the network only through the sources and the keyring read its configuration fixes. `cmd/verify_render.go` writes the report as text, following SPEC.md's display rules (section 11.5), and `--json` writes the report's own encoding. The renderer never grades: every status is decided in a step.
- **Shared UI package**: `internal/ui/ui.go` provides the shared lipgloss v2 styling foundation (adaptive color palette, HeaderBox, SectionHeader, banners). Light/dark support is a Catppuccin palette (Mocha by default) that `ui.Init()` swaps to Latte when the terminal reports a light background; that detection is deliberately deferred out of package init so shell completion cannot hang on SIGTTIN. `--no-color` flag sets `lipgloss.Writer.Profile = NoTTY` to strip all ANSI. The `NO_COLOR` env var is natively respected by lipgloss.
- **`tscrypto` package**: Named to avoid shadowing Go's stdlib `crypto` package. No import alias needed. It holds the constant-time comparisons and the UUIDv7 time reader; the verifier's hashes, and the key id `convert keyid` prints (`verifier.KeyID`, which is `registry.KeyIDOf`, SPEC.md section 3.3), are `internal/registry`'s.
- **Error handling**: `verifier.Verify` gives an `Outcome`: a report, a bare rejection, or a fault with no report (`ErrFault`, exit 2), and an input that cannot be read is an error (exit 1). A check that fails is a `fail` row in the report, never an error.
- **Shared input-selection helper**: `internal/inputsrc.Resolve` / `.ResolveStream` are the single place the six-mode input pattern lives. `verify`, `inspect`, `items create` (via sentinel constants), `hash`, `encode`, `decode` and `jcs` all route through it; the `convert` children read a positional argument or stdin themselves and take no `--file` or `--url`. The `FilePickSentinel = "(pick)"` and `URLPromptSentinel = "(prompt)"` constants are pflag `NoOptDefVal` values chosen for readable `--help` output; they are effectively impossible as real filenames/URLs.
- **JSON is encoding/json/v2, never v1**: every file reads and writes JSON through `encoding/json/v2` and `encoding/json/jsontext`, and `cmd/json_imports_test.go` fails on any import of `encoding/json`. Proofs, keyrings and source answers go through neither: `internal/strictjson` reads them under J1 to J6 of SPEC.md section 10.1, which v2's defaults do not make in full (no size limit, no J5 integer gap, depth 10,000 rather than 32, and -0 kept), and `internal/jcs` writes their canonical form. What v2 adds is strictness everywhere else: a server or GitHub response with a repeated member name or invalid UTF-8 is refused instead of read as v1 would read it (the last of two names, U+FFFD), and a field matches its name exactly, so every struct a response is decoded into is tagged. v2 has no `UseNumber`: a number that must stay as written in an `any` (an entropy record's ledger sequence) is read with `internal/jsonnumber.AsWritten`, which keeps it as the `jsontext.Value` it is written as. Writing, v2 gives a nil list as `[]`, writes `<`, `>` and `&` as themselves, sorts a map's members only under `json.Deterministic(true)`, and rewrites a string a `MarshalJSON` method returns unless `jsontext.PreserveRawStrings(true)` is set. So `emitJSON` (`cmd/output.go`), the one `--json` writer, sets both: without the second, `inspect --json` would print the directional and invisible code points `claimsName.MarshalJSON` escapes (SPEC.md section 3.7) as raw characters. A field that should be left out only when it holds its zero value is tagged `omitzero`, since v2's `omitempty` keeps `false` and `0`.

## CLI behavior

- **Hashes and ids are never truncated in output**: no `…`, no `...`, no slicing, no column width that clips. Every cryptographic value (hash, id, key, signature, Merkle root) renders whole in every output mode: lists, cards, logs, errors, text and `--json`. `beacons list` is the reference implementation, and its source comment states the reason: the whole point of a listing is to surface the value for copy-paste and shell substitution. `cmd/list_full_values_test.go` renders each list from a fixture and fails if any hash or id it was given does not survive intact, or if any elision marker follows a run of hex.

  The argument that the full value is available elsewhere, from the card, from `--json` or from `get`, does not hold: an abbreviated hash cannot be copied, pasted, grepped or piped, which is what a listing is *for*; and the abbreviation is silent, so a reader cannot distinguish a truncated value from a short one. Terminal width is the user's to manage with a pager or `--json`, and is never a reason to discard data. No helper abbreviates a hash or id for display, under any name.

  Two narrow exceptions exist, neither of them display of a value the user asked to see:

  | Site | Why it is not display truncation |
  | ---- | -------------------------------- |
  | `cmd.maskAPIKey`, `internal/config` API-key masking | Protects a credential. The point is that the value is *not* shown. |
  | `internal/verify.truncateToken`, `internal/httpclient.Truncate` | Bounds a hostile or broken server's echoed string so it cannot inject an unbounded value into a rendered report or error. A security control. |

  `internal/registry.KeyIDOf`'s `sum[:4]` is not truncation either: the 4-byte key id is the specified value, not an abbreviation of a longer one. Nor is the item code (SPEC.md section 3.9), a value of its own written from `item_hash`'s leftmost 75 bits and a check symbol: it is printed whole, labelled, beside the whole `item_hash` in `verify` and `inspect`, and never in its place. Likewise `ui.TruncateToSecond` drops sub-second timestamp precision, which is a time-format choice, not a cryptographic value.

- **Trailing guidance is one block, one indent, one style**: the `More:` / `Back:` cursor lines, the page-clamp note, the `Hint:` tips and the empty-state text all go through `cmd.renderListHints` (or at minimum `ui.HintStyle()` + the `cmd.hintIndent` constant). One blank line separates the block from the content above it, emitted once by whichever line comes first and only when there is something to print, so a listing with no continuation and no tip does not end in a stray gap. `cmd/hints_test.go` pins the indent, the separator, the "nothing to print writes nothing" case, and the stream split.

  Two reasons govern it. **Alignment**: every line is inset by `hintIndent` (two spaces), matching the empty-state lines, so a listing's footer never steps in and out under the table. **Contrast**: the guidance is meant to be read, and `ui.FaintStyle()` compounds a low-contrast foreground with the ANSI faint attribute (SGR 2). Measured against each Catppuccin flavour's `Base`:

  | Token | Mocha (dark) | Latte (light) |
  | ----- | ------------ | ------------- |
  | `Overlay0` (`Dim`) | 3.36:1, under AA | **2.30:1, fails outright** |
  | `Subtext0` (`Label`) | 7.37:1 | 4.37:1, just under AA |
  | `Subtext1` (`Hint`) | 9.26:1 | 5.53:1 |
  | `Text` (`Value`) | 11.34:1 | 7.06:1 |

  Light is the worse of the two, and the faint attribute dims it further. `ui.HintStyle()` uses `Subtext1` and does **not** set `Faint(true)`: it clears WCAG AA in both themes while still reading as subordinate to `Value`. `ui.FaintStyle()` remains for decoration the reader is not expected to act on; anything meant to be read (a hint, a cursor to paste, the sole "No blocks." line a command prints) uses `HintStyle`.

  **Guidance is commentary about the output, never the output.** The whole block, cursor lines included, goes to **stderr**, and only when stdout is a terminal. `truestamp entropy list | wc -l` counts rows, and `... > f` writes a file the next command can read.

  A cursor line on stdout would land in every redirected listing and every pipe, and splitting one block across two streams would let its halves interleave out of order once either was redirected. `cmd/hints_test.go` pins the suppression, and the entropy CLI tests assert the pipeline guarantee on *both* streams.

  The gate is `cmd.stdoutIsTerminal`, a package-level seam rather than a direct `inputsrc.IsStdoutTerminal()` call, because `go test` is never a terminal: without it every hint assertion would run against an empty buffer and would keep passing after the text rotted. `cmd/hints_test.go` swaps it through `withTerminalStdout`. The subprocess tests in `cmd/entropy_test.go` cannot reach that seam (they exec a real binary whose stdout is a pipe), so they assert the complementary property: a piped run carries no guidance at all.

- **Post-action card URL shape**: The beacon, proofs get, items create, items get, items update and team cards all share the `ui.SubjectDetailURL` / `ui.SubjectVerifyURL` / `ui.BeaconDetailURL` / `ui.BeaconVerifyURL` helpers in [`internal/ui/weburls.go`](../internal/ui/weburls.go); the same file also exports `ui.TeamDetailURL` / `ui.TeamCreateURL` for the team surfaces. An item's Details and Verify URLs take its item code (`/items/<CODE>`, `/verify/item/<CODE>`, the pages' canonical form), and every other subject's its id. Never hand-build a card URL: every one goes through this file. Every helper goes through one `publicWebBase` function that strips a trailing `/api/json` and emits the URL unconditionally: localhost, 127.0.0.1, and plain-http hosts all render URLs so developers can click through against their dev server. The small tradeoff (a dev-host URL may appear in a shared transcript) is accepted by design.
- **Card vertical spacing**: Every post-action card uses `ui.CompactTable()` which returns a lipgloss table with `HiddenBorder` plus `BorderTop/Bottom/Left/Right(false)`. Without the false flags, HiddenBorder still emits invisible top/bottom border rows that stack with section separators and double the apparent vertical gap between a section header and its first row. Using `CompactTable` keeps the table content flush to whatever precedes/follows it, letting callers control inter-section spacing explicitly with `""` elements in `strings.Join`.
- **Hash command is sha256sum-compatible by default**: `--style gnu` (the default) emits byte-identical output to GNU coreutils' sha256sum (text mode: `<hex>  <filename>\n`, binary mode with `--binary`: `<hex> *<filename>\n`, filenames with `\` or `\n` get the standard `\` line-prefix + `\\` / `\n` escaping). `--style bsd` matches `shasum --tag`. Cross-tool output equivalence is asserted in `cmd/hash_test.go`.
- **Legacy algorithm warning**: `truestamp hash -a md5` and `-a sha1` emit a one-line stderr warning (`warning: <algo> is cryptographically broken and unsuitable for security uses`). Suppressed under `--silent` and `--json`.
- **Two algorithm registries, deliberately not identical**: `internal/hashing.algorithms` is the 14-entry set `truestamp hash` accepts, with its own naming (`blake2s-256`, `blake2b-256/384/512`, aliases `sha3_256` and the like). `internal/verifier`'s `hashHexCharacters` (`expected_hash.go`) is the **12-entry `hash_type` table of SPEC.md section 10.2, step 13 (EXPECTED_HASH)**, each name with the hex length of its hash, locked by `TestExpectedHash_TheTableIsSPECs`. They differ in both cardinality and naming and **must not be "synced"**: the second is SPEC.md's, so widening or narrowing it changes EXPECTED_HASH's row on a proof every other verifier grades alike. Neither is a claims `hash_type` registry: the server decides what `items create` may send, and the CLI makes no local check of it. A future editor who notices the divergence should read this paragraph, not reconcile them.

## Testing

- **CLI integration tests**: `cmd/verify_test.go`'s `TestMain` (`runTests`) builds the actual binary once and runs it as a subprocess to test real exit codes and output, with the environment isolated: a HOME and XDG directories made for the run, no `TRUESTAMP_*` variable but `TRUESTAMP_NO_UPGRADE_CHECK=1`, and a dead loopback `TRUESTAMP_BASE_URL`. An online `verify` test runs a binary whose keyring and NIST addresses are set to a loopback port at link time (`cmd/verify_online_test.go`, `verifierEndpointFlags`, `buildVerifyBinary`), with every source on loopback.
- **No test reaches the network**: `task test-nonet` runs the suite (or one command after `--`) under the macOS no-network guard in `tools/nonet/`, which refuses every connection off loopback and the keychain tool, runs a control that must see each refusal first, and fails a run that passes with a recorded attempt (see `CLAUDE.md`'s hard rule).
- **The spec's copies are synced, never edited**: `task verification-sync` copies the spec into `testdata/verification/` and `internal/specdata/verification/`, and `task verification-check` compares both with the commit `SOURCE` names; `task merkle-vectors-sync` and `task merkle-vectors-check` do the same for `testdata/merkle/` (see [Conformance](#conformance)).
- **Fuzz coverage on every parser**: 54 `FuzzXxx` targets (cmd:7, encoding:5, selfupgrade:5, beacons:4, hashing:4, config:3, external:3, teams:3, tscrypto:3, wschannel:3, auth:2, inputsrc:2, items:2, strictjson:2, upgradecheck:2, jcs:1, jsonapi:1, logging:1, redact:1) cover every parser that touches attacker-controlled bytes (the strict JSON reader, keyring and API response bodies, base64/hex/base64url decoders, Merkle compact proof, TOML config, tar.gz extract path traversal, Phoenix frames, time/ID/URL parsers). Seeds are committed; `go test ./...` replays them as regression tests on every run. Active fuzzing via `task fuzz-deep` (default 15s per target; tune with `DURATION=1m task fuzz-deep`); discovered reproducers are written by the Go fuzz engine under each package's `testdata/fuzz/FuzzXxx/` and MUST be committed so the regular test run replays them as permanent regressions. `task fuzz-list` prints the target inventory; `find . -path '*/testdata/fuzz/*' -type f` after a fuzz-deep session lists any new reproducers to commit.
