# Architecture Notes

Design decisions and their reasoning. Upgrade/install internals live in
[upgrade-and-install.md](upgrade-and-install.md).

## Conformance

- **Appendix E conformance is a maintained property, not a one-off**: `truestamp verify` is written against Appendix E of the whitepaper and self-certifies against it. Three artifacts hold the line, and all three must move together when the appendix does:
  - `internal/verify/conformance_test.go`: runs the three production bundles (`testdata/prod-2026-09-03/`) offline with the production keyring pinned and checks them row for row against the reference verifier's own reports (`standalone-*.txt`), runs the Appendix D bundle (`testdata/whitepaper/bundle.json`) with its own claims hash and checks E.25's **one-way containment** against D.4 (no D.4 row missing or differently graded; additional `skip`/`info` rows allowed; additional `pass`/`fail`/`warn` rows not), runs the tamper table against the reference's and the server's reports, checks that the CBOR bundle yields byte-identical rows to the JSON one, and (with `TRUESTAMP_ONLINE_TESTS=1`) checks an online run against the server's `verify-*.json` reports. `vectors_test.go` reproduces every Appendix C vector and every value in the D.3 derivation trace. `cmd/verify_test.go` repeats the D.4 containment at the process boundary through `--json`.
  - The reference verifier's own printed reports for the three production bundles (`testdata/prod-2026-09-03/standalone-*.txt`) are compared row for row, group and status alike, in category order. Containment alone cannot see a report that *drops* a reference row and appends a fabricated one with the same pair; the row-for-row comparison can. E.25 grades statuses, so this is the CLI going beyond the appendix on purpose.
  - Status choices are pinned by the containment tests above, because Appendix E is, more than anything else, a specification of which condition earns which status: E.18 settles that a Stellar commitment absent from the chain FAILS while an unreachable Horizon SKIPS; E.21 settles the same split for entropy sources; E.22 forbids a skip from reading as a positive assertion. A `fail` silently downgraded to a `skip`, or a `skip` promoted to a `pass`, breaks containment against a report that was produced by a different implementation, which a message assertion alone would not catch.
  - The acceptance run must be **hermetic**. `verify`'s flags are also config keys, so an ambient `TRUESTAMP_VERIFY_SKIP_SIGNATURES` or a `[verify] skip_signatures = true` in config.toml turns D.4's Proof Signature `pass` into a `skip` while the run still exits 0. The exit code is therefore *not* the acceptance criterion; the row census is.
- **The report is graded, not gated (Appendix E.6 / E.22)**: the parser aborts on E.6's enumerated hard rejections and on nothing else. Anything else malformed (a wrong-typed field, a bad hash width, an unrecognized `network`) parses and is reported as a graded step. The reason is comparability: a verifier that refuses to produce a report cannot be compared against one that does, which is the whole point of E.23's rejection vocabulary and E.25's containment check. Correspondingly, an external source that is *unreachable* never fails a proof (E.5): only a source that answered and substantively disagreed does. `internal/external.Classify` is the single place that distinction is made, and `verify.go` grades `Mismatch` as fail and everything else as skip.
- **The filename never decides a subject type (Appendix E.24)**: `truestamp verify`'s `typeFlag` is the value of `--type` and nothing else. The CLI used to infer it from a `truestamp-<stem>-<id>.<ext>` basename, which made the verdict a function of the filename in both directions: a stem disagreeing with the signed type failed a sound proof (a beacon page legitimately serves a `type: block` bundle under a beacon-named file, E.24's own example), and renaming away from a conforming stem silently dropped the assertion. The inference added no detection power either: the type code is inside the signed payload (E.16), so relabelling a bundle already breaks its signature. `cmd/download.go`'s smart default is a **different and legitimate** mechanism: it keys on the *id shape* (ULID means `item`, UUIDv7 means a hard error listing the five valid types) because a download has no bundle to read yet. Do not conflate them. Pinned by `TestCLI_Verify_FilenameNeverAffectsVerdict` and `TestCLI_Verify_TypeAssertion`.
- **Hard rejections carry a machine-readable identifier (Appendix E.23)**: an E.6 rejection aborts before any step runs, so `verify.RunFromBytes` returns a `proof.RejectionError` and there is no `Report`. The terminal prints `REJECTED: <code>`, the detail and one line of advice (`proof.RejectionAdvice`); under `--json`, `cmd/verify.go` emits `{"passed": false, "rejection": {"code", "detail", "advice"}, "steps": []}`. The whole point of the taxonomy is that two independent verifiers can be compared on the identifier without diffing prose. The draft layout is the one rejection that is not a defective bundle but a different layout (`unsupported_layout`), and the `--type` assertion is the one CLI-side rejection (`subject_type_mismatch`, the server's name for it).

  E.23 also carries **step-fail** identifiers, which do *not* route through `proof.RejectionError`: the run continues and produces a full report, so there is no `rejection` object to hang them on. `invalid_hex_encoding` (E.4) is the one the CLI emits, and it rides as a `"<code>: "` prefix on the step's message, the shape the reference verifier uses, chosen so the two reports diff. `internal/verify`'s `codeInvalidHexEncoding` + `withCode` / `hexEncodingAware` are the only writers. If a future identifier needs machine access without string-matching, add a `code` field to the JSON step object rather than widening `RejectionError`.

## Code organization

- **Authentication is a single process-wide chokepoint**: `cmd/root.go`'s `PersistentPreRunE` resolves one `auth.Authorizer` via `auth.Resolve` (precedence: explicit `--api-key`/`TRUESTAMP_API_KEY` → stored OAuth session → config-file `api_key` → none) and installs it with `auth.SetDefault`, mirroring `httpclient`'s package-global pattern so the existing call sites authorize via `auth.AuthorizeRequest`/`auth.Default()` without threading an authorizer through every signature. OAuth and the API key are unified behind the same `Authorizer` (both presented as `Authorization: Bearer <value>` to the JSON API). A reactive **401 → ForceRefresh → retry-once** `http.RoundTripper` (`auth.NewRetryTransport`) is layered onto the shared client via `httpclient.SetTransport`, so a server-rejected OAuth access token self-heals without a spurious auth failure; only OAuth-mode requests *we* authenticated are retried, and a dead session (`invalid_grant` ⇒ `ErrSessionExpired`) is not. OAuth tokens live in the OS keychain (0600-file fallback), never config.toml; the refresh token rotates on every refresh. Full model in [authentication.md](authentication.md).
- **Logic/presentation separation**: `verify.go` orchestrates and the `steps_*.go` files build a `Report` of `Step` rows (pure logic, no I/O except the external lookups behind explicit options). `presenter.go` renders the report in the reference verifier's shape (a bundle header, five categories in E.22's order, badges, counts, verdict) through `lipgloss.Print` so color follows the terminal; `json_output.go` builds the server-shaped JSON document; `report.go` defines the types, the counts and `Passed()`. The presenter never grades: every status decision is made in a step.
- **Shared UI package**: `internal/ui/ui.go` provides the shared lipgloss v2 styling foundation (adaptive color palette, HeaderBox, SectionHeader, banners). Light/dark support is a Catppuccin palette (Mocha by default) that `ui.Init()` swaps to Latte when the terminal reports a light background; that detection is deliberately deferred out of package init so shell completion cannot hang on SIGTTIN. `--no-color` flag sets `lipgloss.Writer.Profile = NoTTY` to strip all ANSI. The `NO_COLOR` env var is natively respected by lipgloss.
- **`tscrypto` package**: Named to avoid shadowing Go's stdlib `crypto` package. No import alias needed.
- **Error handling**: `Run()` returns `(*Report, error)`. `error` for structural failures (missing file, bad JSON). Individual verification failures are `StatusFail` steps in the report.
- **Shared input-selection helper**: `internal/inputsrc.Resolve` / `.ResolveStream` are the single place the six-mode input pattern lives. `verify`, `create` (via sentinel constants), `hash`, `encode`, `decode`, `jcs`, and the `convert` children all route through it. The `FilePickSentinel = "(pick)"` and `URLPromptSentinel = "(prompt)"` constants are pflag `NoOptDefVal` values chosen for readable `--help` output; they are effectively impossible as real filenames/URLs.

## CLI behavior

- **Post-action card URL shape**: The beacon, download, create, and verify cards all share the `ui.SubjectDetailURL` / `ui.SubjectVerifyURL` / `ui.BeaconDetailURL` / `ui.BeaconVerifyURL` helpers in [`internal/ui/weburls.go`](../internal/ui/weburls.go); the same file also exports `ui.TeamDetailURL` / `ui.TeamCreateURL` for the team surfaces. Never hand-build a card URL, every helper must go through this file. Every helper goes through one `publicWebBase` function that strips a trailing `/api/json` and emits the URL unconditionally: localhost, 127.0.0.1, and plain-http hosts all render URLs so developers can click through against their dev server. The small tradeoff (a dev-host URL may appear in a shared transcript) is accepted by design.
- **Card vertical spacing**: Every post-action card uses `ui.CompactTable()` which returns a lipgloss table with `HiddenBorder` plus `BorderTop/Bottom/Left/Right(false)`. Without the false flags, HiddenBorder still emits invisible top/bottom border rows that stack with section separators and double the apparent vertical gap between a section header and its first row. Using `CompactTable` keeps the table content flush to whatever precedes/follows it, letting callers control inter-section spacing explicitly with `""` elements in `strings.Join`.
- **Hash command is sha256sum-compatible by default**: `--style gnu` (the default) emits byte-identical output to GNU coreutils' sha256sum (text mode: `<hex>  <filename>\n`, binary mode with `--binary`: `<hex> *<filename>\n`, filenames with `\` or `\n` get the standard `\` line-prefix + `\\` / `\n` escaping). `--style bsd` matches `shasum --tag`. Cross-tool output equivalence is asserted in `cmd/hash_test.go`.
- **Legacy algorithm warning**: `truestamp hash -a md5` and `-a sha1` emit a one-line stderr warning (`warning: <algo> is cryptographically broken and unsuitable for security uses`). Suppressed under `--silent` and `--json`.
- **Two algorithm registries, deliberately not identical**: `internal/hashing.algorithms` is the 14-entry set `truestamp hash` accepts, with its own naming (`blake2s-256`, `blake2b-256/384/512`). `internal/tscrypto`'s `hashTypes` is the **12-entry Appendix E.11 wire registry**: the exact set the Truestamp backend accepts as a `claims.hash_type`, locked by `TestValidateClaimsHashRegistryMatchesSpec`. They differ in both cardinality and naming and **must not be "synced"**: widening `tscrypto`'s set would accept a `hash_type` the server rejects, and narrowing it would fail sound bundles. A future editor who notices the divergence should read this paragraph, not reconcile them.

## Data handling

- **CBOR is a value-space conversion**: `proof.CBORToJSON` converts a CBOR bundle (tag 55799 or bare) into the equivalent JSON document by Appendix E.3's field-type correspondence, driven by each field's position (`public_key`/`signature` to base64, every hash slot to lowercase hex, every JCS-preimage map kept strictly in the JSON value space, everything else by JSON type), and the same JSON parser then runs, so both serializations grade one bundle identically. `proof.JSONToCBOR` is the exact inverse and uses `cbor.CoreDetEncOptions` (RFC 8949 section 4.2: sorted keys, shortest-form ints, definite-length containers) with the self-describing tag prepended so `IsCBORProof` auto-detects the format on round trips. `Bundle.JSON` keeps the document a bundle was parsed from, so `convert proof --to json` preserves the wire's key order and every number literal.

## Testing

- **CLI integration tests**: `cmd/verify_test.go` builds the actual binary in `TestMain` and runs it as a subprocess to test real exit codes and silent mode.
- **Fuzz coverage on every parser**: 79 `FuzzXxx` targets (tscrypto:11, cmd:8, proof:7, bitcoin:6, encoding:5, external:5, selfupgrade:5, beacons:4, hashing:4, config:3, items:3, teams:3, wschannel:3, auth:2, inputsrc:2, jcs:2, upgradecheck:2, verify:2, logging:1, redact:1) cover every parser that touches attacker-controlled bytes (proof JSON/CBOR, base64/hex/base64url decoders, Merkle compact proof, Bitcoin tx + txoutproof, TOML config, tar.gz extract path traversal, time/ID/URL parsers). Seeds are committed; `go test ./...` replays them as regression tests on every run. Active fuzzing via `task fuzz-deep` (default 15s per target; tune with `DURATION=1m task fuzz-deep`); discovered reproducers are written by the Go fuzz engine under each package's `testdata/fuzz/FuzzXxx/` and MUST be committed so the regular test run replays them as permanent regressions. `task fuzz-list` prints the target inventory; `find . -path '*/testdata/fuzz/*' -type f` after a fuzz-deep session lists any new reproducers to commit.
