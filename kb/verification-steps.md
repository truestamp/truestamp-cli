# Verification steps

`internal/verify` runs Appendix E of `truestamp-v2/whitepaper/whitepaper.typ` in dependency order, and the reference verifier `whitepaper/verify_proof.exs` is the behavioral oracle: step order, status choices and row wording follow it, so that on any bundle the two produce reports whose statuses match per E.25. Read Appendix E and the reference before changing anything here. The orchestration is `runBundle` in [`verify.go`](../internal/verify/verify.go); each step lives in a `steps_*.go` file.

## Order and rows

| Step | Group (E.22) | Category | What it reports |
| ---- | ------------ | -------- | --------------- |
| E.7 | Hash Comparison | Data Integrity | `item` only. Expected hash supplied and `claims.hash` present: trim, downcase, constant-time compare; `pass` or `fail`. Supplied but no `claims.hash`: `warn` (never fail). Not supplied but `claims.hash` present: `warn` "file hash not verified". Neither: `skip`. Any non-item type with a supplied hash: `skip` |
| E.8 | Structure | Structural | `version == 1`, `pass` or `fail` |
| E.4 | Structure | Structural | the lowercase-hex sweep: one `fail` naming every offender, or no row at all |
| E.9 | Signing Key | Cryptographic | `public_key` decodes to 32 bytes; derive `key_id = SHA-256(0x51 \|\| pk)[0..3]` |
| E.10 | Subject Data | Cryptographic | three `pass` rows: data hash (0x11/0x21), metadata hash (0x12/0x22, "which the bundle carries"), composite fingerprint (0x13/0x23, 111- or 121-byte preimage); plus the 2^53 portability `warn` when an integer in the data map exceeds it |
| E.11 | Subject Data | Data Integrity / Timing | `item` only, warn or info, never fail: hash shape for a registered `hash_type` (`info` well formed, `warn` otherwise, both under Data Integrity); a claimed timestamp later than submission or more than 7 days before it (`warn` under Timing) |
| E.13 | Inclusion Proof | Cryptographic | decode, walk from the subject hash, compare to `block.merkle_root`. Block-like: `skip` "not applicable". No subject hash: `fail` "cannot verify" |
| E.14 | Block Hash | Cryptographic | two `pass` rows: block metadata hash (0x33), block hash (0x32, 157-byte preimage, hash printed). Block-like: `subject_hash := block_hash` |
| E.15 | Epoch Proof | Cryptographic | one row per commitment entry in array order, labelled by `chain`: walk from the block hash to that entry's `epoch_merkle_root` |
| E.16 | Proof Signature | Cryptographic | rebuild the 81 + 32N payload (derived key id, `generated_at` ms, subject hash, block hash, N epoch roots), hash under 0x61, verify pure Ed25519. Any missing upstream value: `fail` "cannot verify proof signature (missing derived data): ..." |
| E.17 | Key Binding | Cryptographic | a pinned keyring file (`--keyring`) or, online, the keyring fetched from the configured base URL: `pass` naming sequence and active flag, or `fail` "NOT in the ... keyring". No keyring in hand (offline, none configured, unreachable): `skip` |
| E.17 | Signing Key Event | Cryptographic | absent: one `skip`. Present: five checks, each a row: key_event type in `genesis\|rotation\|emergency_rotation`; `key_event.public_key` equals the bundle's; `key_event.key_id` equals the DERIVED key id; an `info` "key event type X, sequence N"; the key-event block hash derived per E.14; then per commitment entry an E.15 walk from that hash and an E.18/E.19 confirmation (or an offline `skip`). No commitments: `skip`; entries present but none valid: `fail` |
| E.17a | Witnesses | Timing | union of committed and carried names, sorted. Unknown name: `skip`. Committed but not carried: `skip`. Carried but not committed: `fail witness_hash_mismatch`. Both: recompute (block hash for `block`, 0x21 over JCS for entropy), constant-time compare, `pass` or `fail witness_hash_mismatch`. After a matched `block`: the chain link row, exactly one of direct predecessor (`pass`), walked `block_path` (`pass` or `fail block_path_broken`), or neither (`fail block_path_broken`). A matched entropy witness published after the subject's submission time: `warn`. Block-like: one `skip`; no witnesses at all: one `skip` |
| E.18 | Stellar Commitment | Blockchain | online: Horizon lookup by `transaction_hash` (`public` selects the public Horizon, anything else including absent selects testnet); `memo_type` must be `hash` and the memo must equal `epoch_merkle_root` (`pass` "Stellar memo matches expected epoch root"), then the ledger (`pass` "Transaction X confirmed on N (ledger L)"). Mismatch: `fail`. 404 on a named network: `fail`; on the defaulted network: `skip`. No `transaction_hash`, offline, or any transport failure: `skip` |
| E.19 | Bitcoin Commitment | Blockchain | the offline steps over `raw_transaction`, `txoutproof`, `block_merkle_root` are **internal consistency only**, reported in the server's four rows and words (`info` on success, `fail` prefixed "Check failed: " on contradiction, never a passing commitment): the OP_RETURN of the raw transaction equals the epoch root; the txid recomputed from it equals `transaction_hash`; the parsed txoutproof's partial Merkle tree places `transaction_hash` under its header's root; the entry's `block_merkle_root` matches that header. The block hash recomputed from the 80-byte header has no row of its own; it feeds the mandatory binding step, which confirms it at `block_height` via Blockstream (mainnet/testnet) and is the only `pass`. The server has no networked Bitcoin lookup and always skips the binding; this CLI is the stricter verifier E.1 permits. Offline, regtest, an absent `network`, or a missing field: `skip`, with a disclosure info that `network` is not covered by the signature |
| E.21 | Entropy Source | Blockchain | for an entropy subject, re-fetch the source (NIST pulse by chain/pulse index comparing `outputValue` and `timeStamp`; Horizon ledger by sequence comparing `hash` and `closed_at`; Blockstream block by hash comparing `height` and `time`): mismatch `fail`, unavailability `skip`. Then one row per matched carried entropy witness, "<name> witness: ..."; a confirmed witness is what lets Submitted After report a `pass`. A pass establishes existence, never freshness |
| E.20 | Submission Window | Timing | `ULID(subject.id) <= UUIDv7(block.id)`, `pass` "(asserted by Truestamp, not externally verified)" or `fail` "submission-window ordering violation"; none for block-like or when an id does not decode |
| E.20 | Temporal Info | Timing | one `info` "submitted T, committed into a block T" |
| E.20 | Submitted After | Timing | one `info` per carried witness naming its published time and basis; then the operative edge: the LATEST published time among witnesses that matched AND were source-confirmed, as `pass`; else the latest matched witness's time as `info` ("rests on the X witness ... no carried witness was confirmed"); else `info` "no carried witness yielded a source-published time". Compact bundle: exactly one `info` naming the committed witnesses. Block-like: one `skip` |
| E.20 | Submitted Before | Timing | the EARLIEST `timestamp` among commitment entries whose chain confirmed in this run: `pass` naming the chain, plus an `info` for any earlier unconfirmed candidate (which never displaces a confirmed edge). Nothing confirmed: `info` naming the earliest candidate. No timestamps: `info` "not established" |

## What may be skipped, and what may not

Steps that may report `skip` for lack of network or a keyring: E.18, E.19's binding step, E.21, the key event's chain confirmations, and E.17's keyring cross-check. Nothing in E.6 to E.16, E.17a or E.20 may be skipped for that reason. Inapplicability skips are required and reported, not omitted: E.7 for a non-item, E.13/E.17a/Submitted After for block-like, no key event carried, a committed-but-not-carried witness, an unknown witness name. A `skip` is a check this run did not perform, not a check that failed; the terminal report says so under the verdict.

`--skip-signatures` leaves E.16 unperformed and is disclosed: a `skip` plus a `warn` under Proof Signature, `signatures_checked: false` in JSON, and a sentence under the verdict. E.25 does not list E.16 among the steps a run may skip and still call itself verified.

## Reporting model (E.22), verdict, conformance (E.25)

Five statuses; five categories in the fixed display order Data Integrity, Cryptographic, Structural, Timing, Blockchain. The terminal report ([`presenter.go`](../internal/verify/presenter.go)) is the reference verifier's shape: a bundle header, `[PASS]`/`[FAIL]`/`[WARN]`/`[SKIP]`/`[INFO]` badges, the group and message, a counts line, "file hash provided", and the verdict with its two explanatory sentences. The JSON report ([`json_output.go`](../internal/verify/json_output.go)) uses the server's field names (`passed`, `steps[{group,status,category,message}]`, the five counts, `hash_provided`, `expected_hash_provided`, `hash_matched`, `proof_version`, `skipped_external`, `temporal`) plus `verifier` and, for a hard rejection, `rejection {code, detail, advice}`, so a CLI report and an API report are diffable.

The verdict is PASSED when no row is `fail`; warns, skips and infos never fail a proof. Exit 0 when the proof passes, 1 when it fails or is rejected. Chain badges (any "verified on Stellar" claim) come from E.18/E.19 confirmations only, never from a witness row.

E.25's containment is one-way: no row Appendix D.4 (or the reference verifier's report for a given bundle) reports may carry a different status, none may be missing, additional `skip` and `info` rows are conformant, additional `pass`/`fail`/`warn` rows are not. [`conformance_test.go`](../internal/verify/conformance_test.go) checks it against the reference verifier's reports for the three production bundles (row for row, in category order), against D.4 for the Appendix D bundle, against the server's online reports (Key Binding excepted: the CLI pins a keyring and passes, the server skips), and across the tamper table. [`vectors_test.go`](../internal/verify/vectors_test.go) reproduces every Appendix C vector and every value in the D.3 derivation trace.

## The two key ids

The derived key id (`SHA-256(0x51 || public_key)[0..3]`) fills the kid slot of the signed payload, is what the keyring cross-check and the key event compare against, and is never read from the wire. The stored `subject.signing_key_id` and each block map's `signing_key_id` are consumed verbatim in the 0x13/0x23 and 0x32 preimages: those composites were hashed at creation time with the then-current key and are frozen into the Merkle tree. Under key rotation the two differ, and a verifier that feeds the derived id into a preimage, or requires the two to be equal, rejects every rotated proof.

## Remote mode

`verify --remote` posts the bundle (a CBOR input as its JSON conversion) with `skip_external`, `expected_hash` and `type` to `/proof/verify` and reproduces the server's steps. Server-side verification is not part of the independence argument (E.2) and this CLI's own verifier never depends on it. The local E.7 comparison is re-run on the posted bundle, a server row that disagrees with it fails the run, a server verdict with no failing step is given a `Server Verdict` fail row, and a server-side rejection (HTTP 400 `invalid_proof` with an E.23 reason) is rendered exactly like a local one. The same `subject_type_mismatch` rejection is applied locally before anything is posted.
