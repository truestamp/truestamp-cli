# Verification Steps (in execution order)

Step **group names** follow Appendix E.22's table, which is normative; do not rename them casually. The E.22 set emitted by `internal/verify` is: `Hash Comparison`, `Signing Key`, `Key Binding`, `Structure`, `Subject Data`, `Inclusion Proof`, `Block Hash`, `Epoch Proof`, `Proof Signature`, `Submission Window`, `Temporal Info`, `Entropy Source`, `Stellar Commitment`, `Bitcoin Commitment`. Five more groups exist and are **not** in E.22's table, all of them additive `info` / `skip` / `fail`-only and therefore E.25-conformant: `Submitted Before` and `Submitted After` (E.20's two edge-disclosure `info` rows, matching the reference verifier's captions verbatim), `Subject Type` (the `--type` assertion), `Verification Notes` (CLI-local advisories), and `Server Verdict` (reachable only on `--remote`, where it reports that the server's own report could not be read or contradicts itself). Adding a group is cheap; adding one that can emit a `pass` or `warn` is not: E.25 forbids extra rows in those statuses. Keep the source-of-truth `group…` constants in `internal/verify` and this list in sync.

Appendix E.25 governs what a conformant report may contain: it is a **one-way containment** against D.4. Extra `skip` and `info` rows are conformant; extra `fail`, `pass` or `warn` rows are not, because those statuses can move a verdict or read as an assertion. A `skip` is never a failure.

The numbering below is the order `runBundle` performs the steps. The **report renders them grouped by category** (Data Integrity → Cryptographic → Structural → Timing → Blockchain), so the row order you see is not this order; the `--json` `steps` array uses the render order too.

0. **Hash Comparison** -- Only when `--hash` is supplied. On a non-item subject (nothing in the bundle commits to a file hash) it is a `skip`, not a failure (E.7). On an external-hash item verified without `--hash`, a `warn` is filed under the same group.
1. **Signing Key** -- Decode base64 `pk` and derive `kid = truncate4(SHA256(0x51 || pubkey))`. That is the whole step (E.9): it makes **no** comparison against `b.kid` or `s.kid`, because key rotation legitimately puts a different key id in those fields. It also has **no skip branch**: `--skip-signatures` leaves it running and passing, deliberately, because skipping it would let an undecodable `pk` produce a report with no failure in it at all. Verified: `verify … --skip-signatures --json` still emits `pass | Signing Key | Public key valid, key_id: f2c39df9`.
2. **Structure** -- two things, and E.22 names both: `v == 1` (E.8, `verifyVersion`) and E.4's hex-encoding sweep (`verifyHexEncoding`, run earlier in the pipeline — before any hash derivation, as E.4 requires — but filed under this group). The propositions the version row used to also carry moved out of this step: registered `t`, block present and `cx` non-empty became E.6's parse rejections (see [proof-bundle-format.md](proof-bundle-format.md) §"Structural requirements"), which abort before any step runs; the individual block members (`b.id`, `b.ph`, `b.mr`, `b.mh`, `b.kid`) are not rejections — E.6 gates only `b`'s map-ness — and an unusable one is graded by E.14 as a `Block Hash` failure ("Cannot derive block hash: no usable value for …"). On a conforming bundle the sweep is silent, so the binary emits exactly one Structure row; on a bundle with an uppercase hex field it emits a second. See [proof-bundle-format.md](proof-bundle-format.md) §"Hex encoding (E.4)".
3-6. **Subject Data** -- Skipped entirely when `t ∈ {10, 11}` (block-like subjects).
   - **Item proofs (`t == 20`)**: Claims Hash `SHA256(0x11 || JCS(claims))`, Claims Hash Type validation (an `info` row per E.11, not a `pass`), Claims Timestamp check, Item Hash `SHA256(0x13 || len32(id) || len32(claims_hash) || len32(metadata_hash) || len32(signing_key_id))`.
   - **Entropy proofs (`t ∈ {30,31,32}`)**: Entropy Hash `SHA256(0x21 || JCS(entropy))`, Observation Hash `SHA256(0x23 || len32(id) || len32(entropy_hash) || len32(metadata_hash) || len32(signing_key_id))`.
   - A canonicalized `s.d` carrying an integer outside ±2^53 adds one `warn` naming the offender (E.4 portability). It does **not** skip or fail any dependent step: the digest above it is the producer's digest.
7. **Inclusion Proof** -- Decode compact base64url `ip`, RFC 6962 walk: leaf = `SHA256(0x00 || subject_hash_bytes)`, internal = `SHA256(0x01 || left || right)`. Root must match `b.mr`. Skipped entirely when `t ∈ {10, 11}`.
8. **Block Hash** -- Derive block hash: `SHA256(0x32 || len32(id) || len32(ph) || len32(mr) || len32(mh) || len32(kid))`. For block-like subjects (t ∈ {10, 11}), `subject_hash = block_hash`.
10. **Epoch Proof** -- For each `cx` entry: decode `ep`, RFC 6962 Merkle walk using block_hash as leaf, root must match `cx.memo` (Stellar, `t=40`) or `cx.op` (Bitcoin, `t=41`).
11. **Proof Signature** -- Build binary payload (big-endian throughout):

    ```
    v(1) || t(2) || kid(4) || ts_ms(8) || subject_hash(32) || block_hash(32) || N(2) || epoch_roots(32*N)
    ```

    `ts_ms` = milliseconds since Unix epoch (uint64 BE) from `ts`. Compute `SHA256(0x61 || payload)`. Verify Ed25519 signature. Skipped with `--skip-signatures`. Flipping `t` in a bundle without re-signing breaks the signature; this is the mechanism that separates beacon (`t=11`) signatures from block (`t=10`) signatures for the same underlying block, and it is why the filename is never consulted for the subject type (E.24).
11a. **Key Binding** -- Cross-check `pk` against the published keyring endpoint. Only a keyring that *answers* and *disagrees* fails; an unreachable, 404ing, empty or malformed keyring is a `skip`. Skipped with `--skip-signatures` or `--skip-external`. Deliberately performed **after** the signature check, not before: E.16 establishes only that *some* key signed this bundle, and E.17 is the step that turns that into "Truestamp signed it". Reporting the binding first inverts the argument.
12. **Submission Window** -- Skipped entirely when `t ∈ {10, 11}`.
    - **Item proofs**: item time (ULID) before committed block time (UUIDv7).
    - **Entropy proofs**: entropy observation time (UUIDv7) before committed block time (UUIDv7).
13. **Temporal Info**, plus E.20's two edge rows -- `Temporal Info` carries the display timestamps (submitted/captured/committed) as a Timing/`info` row. For non-block-like subjects two further `info` rows say which temporal edge the bundle can and cannot establish: `Submitted Before` names the earliest commitment whose on-chain confirmation would establish the earlier edge, and `Submitted After` states that the later edge is **not established from this bundle**, because it needs the referenced previous block and its entropy leaves, which a bundle does not carry. E.20 makes reporting the second a MUST.
14. **Entropy Source** -- For entropy subjects, confirm `s.d` matches the canonical published value at the upstream source. Skipped under `--skip-external`. A 404 at the source is a `skip` on all three (E.21), as are transport errors, timeouts, 5xx and 429; only a lookup that answers and disagrees fails.
   - **NIST Beacon** (`t=30`): `GET beacon.nist.gov/beacon/2.0/chain/{chainIndex}/pulse/{pulseIndex}`; byte-compare `outputValue` and `timeStamp`. RSA signature / X.509 chain verification is out of scope: the server stores only the minimal pulse fields (`chainIndex`, `pulseIndex`, `outputValue`, `timeStamp`, `version`), so the bytes needed to reconstruct NIST's signed pre-image aren't in the bundle.
   - **Stellar ledger** (`t=31`): `GET {horizon}/ledgers/{sequence}`; byte-compare `hash` and `closed_at`. Network is derived from the bundle's Stellar commitment in `cx[]` (`testnet` in dev, `public` in prod): a given Truestamp deployment uses one Stellar network for both entropy and commitment.
   - **Bitcoin block** (`t=32`): `GET blockstream.info/api/block/{hash}`; byte-compare `height` and `time`. Always pinned to **mainnet** regardless of the commitment chain's network: the server observes mainnet as the authoritative public-randomness source even in dev deployments that commit to regtest/testnet.
15. **Stellar Commitment** -- External: GET Horizon API, verify memo and ledger number. An absent or unrecognized `net` resolves to the testnet Horizon (E.5/E.18) and a 404 there is a `skip`; a 404 on an *explicitly named* network is a `fail` (the commitment transaction was asserted to exist on a named chain and does not).
16. **Bitcoin Commitment** -- Local: OP_RETURN extraction, txid computation, CMerkleBlock parsing, partial merkle tree verification; these keep their `pass` status offline (E.19b). External confirmation: GET Blockstream API for mainnet/testnet; regtest has no public API, so confirmation is a `skip`, as is an entry carrying no `rtx` / `txp` / `bmr` to check.

The legacy "subject `kid` must equal block `kid`" check has been removed: key rotation can legitimately produce divergent kids, and subject-kid tampering is still detected because `kid` is an input to the subject composite hash (0x13 / 0x23).

## External confirmation is tri-state

`verify.CommitmentInfo.ExternalCheck` is `ExternalConfirmed` | `ExternalSkipped` | `ExternalFailed`. Only a lookup that *ran and agreed* may be reported as confirmed; the terminal render distinguishes `(external verification skipped)` from `(external verification failed)`. The `--json` `commitments.<chain>.externally_verified` boolean is `true` only for `ExternalConfirmed`, so it collapses the other two.
