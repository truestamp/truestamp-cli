# Commit Message Format Rules

## Subject Line (First Line)

### Character Limit: 50 characters maximum

Count characters carefully. This limit is strictly enforced.

Examples:

| Subject | Length | Valid |
|---------|--------|-------|
| "Add vuln-check to precommit" | 28 | yes |
| "Fix self-upgrade backup pruning" | 31 | yes |
| "Refactor inputsrc into shared package" | 38 | yes |
| "Pin staticcheck and gosec via mise" | 35 | yes |
| "Refactored the input resolver to handle all six modes" | 53 | no |

### Imperative Mood

Write as if completing: "If applied, this commit will..."

Correct (imperative): Add, Fix, Refactor, Update, Remove, Implement,
Extract, Rename, Replace, Simplify, Move, Pin, Bump

Wrong (past tense): Added, Fixed, Refactored, Updated

Wrong (gerund): Adding, Fixing, Refactoring, Updating

### Be Specific

Good:
- "Add --type flag to verify subcommand"
- "Fix detached HEAD warning in upgrade flow"
- "Refactor tscrypto hash domain prefixes"

Bad:
- "Update code"
- "Fix bug"
- "Make improvements"
- "Various changes"

### Other Subject Rules

- Capitalize the first word
- No trailing period
- No prefix conventions (no "feat:", "fix:", etc. — those are for
  Conventional Commits, which this repo does not use)

## Second Line

MUST be blank. This separates the subject from the body.

## Body

### Character Limit: 72 characters per line

Hard wrap at 72 characters. This ensures readability in terminals
and git/jj tools that don't soft-wrap.

### Plain Text Only

Forbidden:
- Markdown headers: ##, ###
- Bold/italic: **text**, *text*
- Links: [text](url)
- Code blocks: triple backticks

Allowed:
- Plain text paragraphs
- Bullet points with "- " prefix
- Inline identifiers when clarity helps

### Structure

```
Subject line in imperative mood (50 chars max)

Body paragraph explaining the motivation and context
for the change. Why was this needed? What problem does
it solve? Wrap at 72 characters.

- Bullet point for a specific change
- Another bullet point
- Additional context if needed

Optional closing paragraph with implications or notes.
```

### What to Include

1. WHY the change was made (motivation)
2. WHAT changed at a high level
3. IMPACT on users or the system

### What to Exclude

- Attribution lines (Co-Authored-By, Signed-off-by, etc.)
- Any credit to AI tools, Claude, or similar
- Issue/PR references in body (jj handles these separately)
- Excessive implementation details (the diff has those)
- Line-by-line narration of what was changed

### When Body Is Optional

Small, self-explanatory changes don't need a body:
- Dependency bumps: "Bump go-toolchain to 1.26.3"
- Typo fixes: "Fix typo in verify help text"
- Single-line config changes
- go.sum-only updates after a clean go.mod edit

If the subject line tells the whole story, stop there.

 1                                                72

## NEVER Include Attribution

This is non-negotiable. Commit messages represent the developer's
voice in the permanent project history. Never append:

- Co-Authored-By: ...
- Signed-off-by: ...
- Generated by ...
- Created with ...
- Any line crediting Claude, AI, or any tool
